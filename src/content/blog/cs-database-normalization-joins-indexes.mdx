주문을 조회할 때는 고객 이름도 보고 싶습니다. 가장 단순한 방법은 주문 행마다 고객 이름을 함께 저장하는 것입니다. 하지만 한 고객이 여러 번 주문하면 이름이 반복되고, 이름을 바꿀 때 여러 행을 수정해야 합니다. 이름을 별도 테이블로 옮기면 중복은 줄지만, 이번에는 두 테이블의 값을 다시 연결해야 합니다. 데이터가 많아지면 그 연결과 조회에 어떤 경로를 쓸지도 중요해집니다.

정규화, 조인, 인덱스는 각각 이 세 질문에 답합니다. 그 전에 데이터베이스가 무엇을 관리하는지, 테이블의 키와 트랜잭션이 어떤 역할을 하는지부터 짚어 보겠습니다. 아래의 고객·주문 데이터는 개념을 설명하기 위한 예시입니다. 특정 서비스에서 측정한 결과는 아닙니다.

## 데이터베이스의 기본 단위: 테이블, 행, 열

**데이터베이스**는 관련된 데이터를 저장하고 조회할 수 있게 조직한 집합입니다. 이를 관리하는 소프트웨어가 <strong>DBMS(Database Management System)</strong>입니다. PostgreSQL 같은 <strong>관계형 DBMS(RDBMS)</strong>는 데이터를 주로 테이블이라는 형태로 다룹니다. 열의 데이터 타입과 제약조건을 정의하고 여러 사용자의 읽기·쓰기를 조정합니다. [PostgreSQL 관계형 데이터 개념](https://www.postgresql.org/docs/current/tutorial-concepts.html)

테이블을 스프레드시트처럼 보면 처음 구조를 이해하기 쉽습니다. `orders_flat`이라는 테이블에서 **행(row)** 하나는 주문 한 건이고, `order_id`, `customer_id`, `customer_name`, `item_name`은 <strong>열(column)</strong>입니다. 열마다 `bigint`, `text` 같은 데이터 타입을 정합니다. 테이블 이름·열 이름·타입·제약조건 등 데이터의 구조를 정의한 것을 <strong>스키마(schema)</strong>라고 부릅니다. 행은 시간이 지나며 늘거나 줄지만 스키마는 별도의 변경 작업으로 수정합니다.

이 구조에서 `order_id`는 주문을 구별하는 값입니다. 반면 `customer_id`는 어떤 고객의 주문인지를 나타냅니다. 숫자가 같아 보여도 두 열의 역할은 다릅니다. 아래에서 기본 키와 외래 키로 이 차이를 다시 살펴보겠습니다.

데이터를 읽고 바꾸는 언어는 **SQL**입니다. 예를 들어 다음 쿼리는 고객 1의 주문에서 두 열을 선택하고, 주문 번호 순으로 결과를 정렬합니다.

```sql
SELECT order_id, item_name
FROM orders_flat
WHERE customer_id = 1
ORDER BY order_id;
```

`SELECT`는 결과에 보여줄 열, `FROM`은 읽을 테이블, `WHERE`는 남길 행의 조건입니다. `ORDER BY`를 지정하지 않으면 결과 행의 순서는 보장되지 않습니다. 저장된 행이 화면에 우연히 같은 순서로 보이더라도 그 순서에 의존해서는 안 됩니다. SQL에는 이 밖에도 행을 추가하는 `INSERT`, 값을 바꾸는 `UPDATE`, 행을 지우는 `DELETE`가 있습니다. [PostgreSQL SQL 튜토리얼](https://www.postgresql.org/docs/current/tutorial-sql.html)

## 정규화: 같은 사실을 어디에 저장할까요?

다음처럼 주문 한 건을 한 행에 저장한다고 가정해 보겠습니다.

| order_id | customer_id | customer_name | item_name |
| --- | --- | --- | --- |
| 101 | 1 | 김민지 | 키보드 |
| 102 | 1 | 김민지 | 마우스 |
| 103 | 2 | 이준 | 모니터 |

`order_id`는 주문을 식별합니다. 그런데 고객 이름은 주문이 아니라 고객에 대한 사실입니다. `customer_id`가 1이면 `customer_name`은 김민지로 정해집니다. 이를 `customer_id → customer_name`이라는 **함수 종속**으로 표현할 수 있습니다. 주문이 늘어날수록 같은 고객 이름도 반복 저장됩니다.

<NormalizationDemo />

고객 1의 이름을 김민아로 바꾸면서 주문 101만 수정하면, 같은 `customer_id`에 두 이름이 남습니다. 이런 문제를 **갱신 이상**이라고 합니다. 해결하려면 고객의 사실을 `customers`에, 주문의 사실을 `orders`에 두고 `customer_id`로 연결할 수 있습니다.

```sql
CREATE TABLE customers (
  customer_id bigint PRIMARY KEY,
  customer_name text NOT NULL
);

CREATE TABLE orders (
  order_id bigint PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers (customer_id),
  item_name text NOT NULL
);
```

`PRIMARY KEY`는 각 행을 구별하며 `NULL`과 중복을 허용하지 않습니다. `orders.customer_id`의 `REFERENCES`는 **외래 키** 제약입니다. 주문이 가리키는 고객이 `customers`에 있는지 검사해, 존재하지 않는 고객 ID가 들어가는 일을 막습니다. 여러 주문이 고객 1을 함께 가리킬 수 있으므로 외래 키 열의 값 자체는 중복될 수 있습니다. `NOT NULL`은 그 열의 값을 비워 둘 수 없게 합니다. 이처럼 제약조건은 데이터가 들어올 때 지켜야 할 규칙입니다. [PostgreSQL 제약조건 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)

뒤의 조인 예시에는 다음 세 고객과 세 주문을 사용합니다. 박서연은 고객 테이블에만 있고 아직 주문이 없습니다.

```sql
INSERT INTO customers (customer_id, customer_name)
VALUES (1, '김민아'), (2, '이준'), (3, '박서연');

INSERT INTO orders (order_id, customer_id, item_name)
VALUES (101, 1, '키보드'), (102, 1, '마우스'), (103, 2, '모니터');
```

<RelationMapMotion />

외래 키는 두 테이블 사이의 **참조가 유효한지 검사**합니다. 뒤에서 사용할 `JOIN`은 조회할 때 그 참조를 따라 **결과 행을 구성**합니다. 이름이 비슷하게 등장하지만 담당하는 일이 다릅니다.

이 예시의 분리는 제3정규형에서 피하려는 **이행 종속**을 이해하는 데 도움이 됩니다. 원래 표에서는 `order_id → customer_id → customer_name`으로 이어집니다. 분리한 뒤 고객 이름은 고객 키에 직접 의존하고, 주문에는 고객을 참조하는 키만 남습니다. 다만 정규형 전체를 이 예시 하나로 판정할 수는 없습니다. 제1정규형은 한 칸에 여러 값을 넣지 않는 문제를, 제2정규형은 복합 키 일부에만 의존하는 속성을 따로 다룹니다. [IBM의 정규화 설명](https://www.ibm.com/think/topics/database-normalization)은 이 단계와 갱신 이상의 관계를 예시로 설명합니다.

테이블을 분리했다고 해서 모든 중복이 잘못이라는 뜻은 아닙니다. 예를 들어 주문 당시의 상품명이나 가격을 **거래 기록**으로 보존하려는 경우에는 현재 상품 정보와 별도로 저장할 이유가 있습니다. 어떤 사실의 원본을 어디에 둘지 먼저 정해야 합니다.

중복이 낳는 문제는 이름 변경에 그치지 않습니다. 주문과 고객을 한 표에만 둔다면 주문이 아직 없는 고객을 등록할 자리가 없습니다. 이것은 **삽입 이상**입니다. 고객의 마지막 주문을 삭제할 때 고객 정보까지 사라지는 것은 **삭제 이상**입니다. 테이블을 나누면 고객의 존재와 주문의 존재를 각각 기록할 수 있습니다.

## 트랜잭션: 여러 변경을 어디까지 한 작업으로 볼까요?

스키마가 분리되면 한 번의 업무가 여러 SQL 문장에 걸칠 수 있습니다. 앞의 3명·3건 데이터를 복제한 별도 상황에서 새 고객 4를 등록하고 그 고객의 첫 주문 104를 저장한다고 가정해 보겠습니다. 고객 추가만 성공하고 주문 추가가 실패한다면, 이 둘을 한 묶음으로 처리할지 결정해야 합니다. 뒤의 조인 데모는 고객 4를 추가하기 전의 데이터를 사용합니다.

**트랜잭션**은 여러 변경을 하나의 작업 단위로 묶습니다. PostgreSQL에서는 `BEGIN`으로 시작하고, 모두 성공했을 때 `COMMIT`으로 반영합니다. 중간에 실패해 작업을 취소해야 하면 `ROLLBACK`을 실행합니다. 그림의 두 경로는 같은 시작 상태에서 각각 성공과 실패를 가정합니다.

<TransactionMotion />

```sql
BEGIN;

INSERT INTO customers (customer_id, customer_name)
VALUES (4, '최하나');

INSERT INTO orders (order_id, customer_id, item_name)
VALUES (104, 4, '헤드셋');

COMMIT;
```

두 번째 `INSERT`가 실패해 트랜잭션을 취소한다면 `COMMIT` 대신 `ROLLBACK`을 실행합니다. 그러면 먼저 성공한 고객 4의 추가도 함께 취소됩니다. 이를 트랜잭션의 <strong>원자성(atomicity)</strong>이라고 합니다. 다른 트랜잭션이 진행 중인 변경을 어떻게 볼지는 격리 수준과 연결되고, 커밋한 변경을 장애 후에도 보존하는 것은 지속성과 연결됩니다. 이 글의 그림은 그중 원자성에 집중합니다. [PostgreSQL 트랜잭션 튜토리얼](https://www.postgresql.org/docs/current/tutorial-transactions.html)

## 조인: 나뉜 행을 어떤 조건으로 연결할까요?

고객과 주문을 분리한 뒤, 주문 내역에 고객 이름을 붙이려면 `customer_id`가 같은 행을 연결합니다. `INNER JOIN`은 양쪽에서 조건에 맞는 행만 결과에 넣습니다.

```sql
SELECT c.customer_name, o.order_id, o.item_name
FROM customers AS c
INNER JOIN orders AS o
  ON o.customer_id = c.customer_id
ORDER BY c.customer_id, o.order_id;
```

고객 1은 주문이 두 건이므로 결과에도 두 행으로 나타납니다. 여기서 조인은 고객 한 행에 주문을 하나만 붙이는 작업이 아닙니다. **조건에 맞는 행의 쌍을 결과로 만드는 작업**입니다.

주문이 없는 고객까지 목록에 남겨야 한다면 `LEFT JOIN`을 사용합니다. 다음 데모에서 박서연의 행이 어떻게 달라지는지 확인해 보세요.

<JoinDemo />

```sql
SELECT c.customer_name, o.order_id, o.item_name
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
ORDER BY c.customer_id, o.order_id;
```

`LEFT JOIN` 결과에서 연결되는 주문이 없으면 주문 쪽 열은 `NULL`입니다. 이때 `WHERE o.order_id IS NOT NULL`을 추가하면 주문이 없는 고객은 다시 걸러집니다. 고객을 모두 남기는 것이 목적이라면 `WHERE` 조건이 그 행을 제거하지 않는지도 살펴야 합니다. PostgreSQL의 [조인 튜토리얼](https://www.postgresql.org/docs/current/tutorial-join.html)도 내부 조인과 왼쪽 외부 조인의 결과 차이를 같은 방식으로 설명합니다.

`NULL`은 빈 문자열이나 숫자 0이 아닙니다. 값이 없거나 알려져 있지 않은 상태를 표현합니다. 따라서 `o.order_id = NULL`이 아니라 `o.order_id IS NULL`처럼 검사해야 합니다. `LEFT JOIN`에서 오른쪽 행이 없을 때 만들어진 `NULL`을 찾으면 주문이 없는 고객만 뽑을 수도 있습니다.

조인은 **어떤 행을 결과에 남길지**를 정하는 SQL의 의미입니다. 데이터베이스가 그 결과를 실제로 만드는 과정에서는 중첩 루프, 해시 조인, 병합 조인처럼 서로 다른 실행 방법을 선택할 수 있습니다. 조인 문법만 보고 한 가지 실행 방법을 단정할 수는 없습니다.

## 인덱스: 필요한 행에 어떻게 도달할까요?

이제 `order_id = 103`인 주문을 찾는다고 가정하겠습니다. 테이블의 행을 차례로 읽어서 찾을 수도 있고, 정렬된 인덱스를 통해 후보 위치를 좁힐 수도 있습니다. 다음 그림은 주문이 101부터 108까지 있는 작은 예시를 사용합니다.

<IndexLookupDemo />

인덱스는 테이블의 모든 열을 복제한 두 번째 테이블이라고 생각하면 부정확합니다. PostgreSQL의 B-tree 인덱스는 내부 페이지를 따라 내려가고, 리프 페이지에서 테이블 행을 가리키는 항목을 찾습니다. 위 그림은 분기에서 범위를 고르고 행에 도달하는 개념만 단순화했습니다. 실제 B-tree의 페이지 구성이나 디스크 읽기 횟수를 재현한 것은 아닙니다. [PostgreSQL B-tree 구조](https://www.postgresql.org/docs/current/btree.html)

앞서 만든 `orders`의 `order_id`는 기본 키입니다. PostgreSQL에서는 기본 키를 만들면 해당 열에 고유 B-tree 인덱스가 자동으로 생기므로 같은 열에 동일한 인덱스를 다시 만들 필요가 없습니다. 반면 고객별 주문을 자주 찾는다면 `customer_id` 인덱스를 검토할 수 있습니다. [PostgreSQL 기본 키 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)

인덱스를 생각할 때는 **어떤 조건으로 찾는지**가 출발점입니다. `order_id = 103`처럼 적은 행을 정확히 찾는 경우와 모든 주문을 읽는 경우는 유리한 접근 방법이 다릅니다. `WHERE customer_id = 1`에 맞는 주문이 전체의 대부분이라면, 인덱스에서 많은 위치를 얻은 뒤 테이블 행을 다시 읽는 작업보다 테이블을 순서대로 읽는 편이 저렴할 수도 있습니다. 인덱스가 있느냐보다 실제 데이터 분포와 쿼리 조건이 중요합니다.

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

EXPLAIN
SELECT order_id, item_name
FROM orders
WHERE customer_id = 1;
```

인덱스를 만들었다고 위 쿼리가 언제나 인덱스 스캔을 택하는 것은 아닙니다. 표가 작거나 조건에 맞는 행이 많으면 순차 스캔의 비용이 더 낮을 수 있습니다. 인덱스 자체도 저장 공간을 쓰고, 데이터를 추가·수정·삭제할 때 유지 비용이 듭니다. 쿼리 조건과 데이터 규모를 놓고 `EXPLAIN`으로 실행 계획을 확인해야 합니다. 실제 실행 시간을 비교하려면 같은 데이터와 환경에서 `EXPLAIN (ANALYZE, BUFFERS)`를 살펴볼 수 있지만, 그 수치를 이 데모의 단계 수와 연결해서는 안 됩니다. [PostgreSQL EXPLAIN 설명](https://www.postgresql.org/docs/current/using-explain.html)

실행 계획에서 `Seq Scan`은 테이블을 순서대로 읽는 계획, `Index Scan`은 인덱스를 이용하는 계획입니다. `EXPLAIN`의 비용 값은 밀리초가 아니라 계획을 비교하기 위한 추정치입니다. 인덱스 효과를 설명할 때는 이 차이도 함께 확인해야 합니다.

## 세 개념을 함께 보면

테이블과 키는 데이터의 모양과 참조 규칙을 정하고, 트랜잭션은 여러 변경을 한 작업으로 다룹니다. 정규화는 고객 이름처럼 **한 가지 사실을 어디에 저장할지** 결정합니다. 조인은 나뉜 고객과 주문을 **어떤 조건으로 다시 읽을지** 결정합니다. 인덱스는 그 조회에서 필요한 행에 **어떤 경로로 접근할지**와 관련됩니다.

설계 순서는 언제나 똑같지 않습니다. 먼저 데이터의 의미와 조회 요구를 정하고, 테이블 사이의 관계를 모델링한 뒤, 실제로 자주 실행되는 쿼리와 실행 계획을 보며 인덱스를 선택하는 편이 좋습니다. 이 글의 작은 표는 원리를 보여주지만 실제 성능을 예측해 주지는 않습니다.
