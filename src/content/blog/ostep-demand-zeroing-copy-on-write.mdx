OSTEP 23장 *Complete Virtual Memory Systems*는 앞 장들에서 따로 배운 메커니즘이 실제 운영체제 안에서 어떻게 합쳐지는지 보여 줍니다. 첫 사례는 DEC 가 1970년대 후반에 내놓은 VAX-11 미니컴퓨터와 그 운영체제 VAX/VMS 입니다. 처음에는 50년 가까이 된 운영체제의 구현을 읽는 일이 JVM 애플리케이션을 운영하는 일과 무슨 관계가 있을지 잘 떠오르지 않았습니다.

그런데 VMS 절의 마지막 "Other Neat Tricks"에 나오는 두 기법, **demand zeroing** 과 **copy-on-write(COW)** 는 지금 Linux 에서도 그대로 쓰입니다. `-Xmx2g` 로 띄운 JVM 의 RSS 가 2GB 보다 훨씬 작게 시작하는 이유와, 1GB 를 쓰는 프로세스가 `fork()` 를 호출해도 메모리가 1GB 늘지 않는 이유가 이 두 기법에 있습니다. 그래서 23장을 읽으며 다음 질문이 생겼습니다.

> 운영체제는 왜 메모리 작업을 요청받은 순간에 하지 않고 미룰까요? 미룬 작업의 비용은 언제, 어디서 치르게 될까요?

이 글에서는 OSTEP 이 설명하는 VMS 의 두 기법을 먼저 정리하고, Linux 의 page fault 처리와 JVM 힙 설정, `fork()` 와 `exec()` 에 차례로 연결합니다. OSTEP 과 Linux 커널 문서, man page, Oracle Java 문서를 읽고 정리한 내용입니다. 확인용 실험 코드를 함께 실었지만 직접 실행한 결과는 포함하지 않았고, 예상 결과는 동작 원리에서 추론한 것입니다. 페이지 크기는 x86-64 Linux 의 기본값인 4KB 를 기준으로 설명합니다.

## 1. 작업을 미루는 것이 왜 최적화일까요?

최적화라고 하면 보통 같은 작업을 더 빨리 끝내는 방법을 떠올립니다. OSTEP 은 demand zeroing 과 COW 를 "lazy optimization"이라고 부르는데, 이 두 기법은 작업을 빨리 하는 대신 작업을 할 시점을 늦춥니다.

23장의 TIP: BE LAZY 는 미루기의 이점을 이렇게 설명합니다. 작업을 미루면 지금 처리 중인 요청의 지연이 줄어듭니다. 운영체제가 파일 쓰기를 곧바로 성공으로 알리고 디스크에는 나중에 백그라운드에서 쓰는 것이 그 예입니다. 더 큰 이점은 미룬 작업을 끝내 하지 않아도 될 때가 있다는 점입니다. 파일 쓰기를 미루는 동안 그 파일이 삭제되면 디스크에 쓸 필요가 없어집니다.

메모리에 대입해 보겠습니다. 프로그램이 100MB 를 요청하고 실제로는 20MB 만 쓴다고 가정합니다.

| 방식 | 요청한 순간 | 처음 접근하는 순간 | 끝까지 접근하지 않은 80MB |
|---|---|---|---|
| eager | 물리 페이지 100MB 를 할당하고 0으로 채운 뒤 매핑합니다 | 추가 작업이 없습니다 | 할당하고 채운 작업이 낭비됩니다 |
| lazy | 가상 주소 영역만 만듭니다 | 그 페이지만 할당하고 0으로 채운 뒤 매핑합니다 | 아무 작업도 하지 않습니다 |

lazy 방식에서는 요청 자체가 빨리 끝나고, 쓰지 않은 80MB 는 물리 메모리를 차지하지 않습니다. 대신 처음 접근하는 페이지마다 운영체제가 개입하는 비용이 생깁니다. 이 비용은 7절에서 다시 다룹니다.

## 2. 메모리를 할당하면 RAM 도 바로 쓰일까요?

demand zeroing 을 이해하려면 주소 공간에 페이지를 추가하는 일과 그 페이지에 물리 프레임을 연결하는 일을 나눠야 합니다.

프로세스가 힙을 늘리면 운영체제는 그 프로세스의 가상 주소 공간에 새 영역을 추가합니다. 이 영역의 주소는 이제 프로세스가 써도 되는 주소입니다. 하지만 그 순간 각 가상 페이지가 물리 프레임에 매핑되어 있을 필요는 없습니다. 운영체제는 프로그램이 그 페이지에 실제로 접근할 때까지 프레임을 준비하는 일을 미룰 수 있습니다.

| 단계 | 하는 일 | 드러나는 지표 |
|---|---|---|
| 주소 공간에 영역 추가 | 프로세스가 써도 되는 가상 주소 범위를 정합니다 | 가상 메모리 크기(VSZ) |
| 물리 페이지 준비 | RAM 의 프레임을 할당하고 초기 내용을 채워 매핑합니다 | RSS |

Linux 에서 파일과 연결되지 않은 이런 메모리를 anonymous memory 라고 부릅니다. 힙, 스택, `MAP_ANONYMOUS` 로 만든 `mmap` 영역이 여기에 속합니다. 이 글에서 다루는 demand zeroing 은 anonymous memory 에 해당합니다. 파일과 연결된 페이지는 처음 접근할 때 0이 아닌 파일 내용을 읽어 와야 하므로 처리가 다릅니다.

## 3. 새 페이지는 왜 0으로 채워야 할까요?

물리 프레임은 여러 프로세스가 돌려 가며 씁니다. 프로세스 A 가 비밀번호나 세션 토큰을 담았던 프레임을 반환하고, 운영체제가 그 프레임을 그대로 프로세스 B 에 준다고 가정합니다. B 는 새로 받은 메모리를 읽기만 해도 A 의 데이터를 볼 수 있습니다. OSTEP 도 새 페이지를 0으로 채우는 이유를 보안으로 설명합니다.

그래서 OSTEP 은 힙에 페이지를 추가하는 가장 단순한 구현을 이렇게 설명합니다.

1. 물리 메모리에서 빈 프레임을 찾습니다.
2. 프레임 전체를 0으로 채웁니다.
3. 페이지 테이블이 그 프레임을 가리키도록 매핑합니다.

이 구현은 프로세스가 그 페이지를 한 번도 쓰지 않을 때 비용이 큽니다. 4KB 를 0으로 채우는 작업과 프레임 하나를 그대로 버리게 됩니다.

## 4. demand zeroing 은 어떻게 동작할까요?

VMS 는 페이지를 추가할 때 거의 아무 작업도 하지 않습니다. 페이지 테이블에 엔트리를 하나 넣고 그 페이지를 접근할 수 없는 상태로 표시합니다. 이 엔트리가 demand-zero 페이지라는 사실은 PTE 에서 운영체제용으로 남겨 둔 비트에 기록합니다. 아직 물리 프레임은 없습니다.

프로세스가 이 페이지를 읽거나 쓰면 다음 순서로 처리됩니다.

1. 하드웨어가 접근할 수 없는 페이지라는 것을 발견하고 운영체제로 트랩합니다.
2. 운영체제는 PTE 의 운영체제용 비트를 읽어 demand-zero 페이지인지 확인합니다.
3. 맞으면 빈 프레임을 찾고 0으로 채운 뒤 페이지 테이블에 매핑합니다.
4. 트랩에서 돌아와 프로세스가 같은 명령을 다시 실행합니다. 이번에는 접근이 성공합니다.

```c
ptr[0] = 10;   // 처음 쓰는 순간 트랩이 일어나고, 운영체제가 0으로 채운 페이지를 매핑한 뒤 다시 실행합니다
```

3절의 단순한 구현과 같은 작업을 첫 접근 시점으로 옮긴 것입니다. 프로세스가 끝내 그 페이지에 접근하지 않으면 프레임 할당과 0 채우기를 모두 건너뜁니다.

### Linux 에서는 어떻게 다를까요?

OSTEP 은 23장의 Linux 절에서 Linux 도 페이지를 demand zero 한다고 짧게 적습니다. 다만 Linux 는 읽기와 쓰기를 다르게 처리합니다.

| 첫 접근 | Linux 의 처리 |
|---|---|
| 읽기 | 0으로 채워진 공유 zero page 를 읽기 전용으로 매핑합니다. 새 프레임은 할당하지 않습니다 |
| 쓰기 | 새 프레임을 할당하고 0으로 채워 쓰기 가능하게 매핑합니다 |
| zero page 를 매핑한 뒤 쓰기 | 쓰기 보호 때문에 다시 page fault 가 나고, 그때 새 프레임을 할당합니다 |

읽기만 하는 페이지는 시스템 전체가 zero page 하나를 같이 씁니다. 그래서 큰 배열을 할당하고 읽기만 하면 RSS 가 거의 늘지 않습니다. 실제 동작은 커널 설정과 transparent huge page 사용 여부에 따라 조금씩 다릅니다.

## 5. `-Xmx2g` 로 실행하면 RAM 2GB 를 바로 쓸까요?

Java 서비스를 이렇게 실행하는 경우가 많습니다.

```bash
java -Xms512m -Xmx2g -jar app.jar
```

[Oracle java 명령 문서](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html)는 `-Xms` 를 힙의 최소 크기이자 초기 크기로, `-Xmx` 를 힙의 최대 크기로 설명합니다. 처음에는 이 설정이면 JVM 이 시작하자마자 RAM 을 512MB 쓰고 최대 2GB 까지 늘어난다고 생각했습니다. 실제로는 시작 직후 RSS 가 512MB 에도 미치지 않을 수 있습니다. HotSpot 이 힙에 쓰는 메모리는 세 단계로 나뉘기 때문입니다.

| 단계 | 의미 | 이 설정에서의 크기 |
|---|---|---|
| reserved | JVM 이 힙으로 쓰려고 예약한 가상 주소 범위 | `-Xmx` 만큼인 2GB |
| committed | JVM 이 운영체제에 실제로 쓰겠다고 요청한 범위. `Runtime.totalMemory()` 가 이 값을 돌려줍니다 | 시작할 때 `-Xms` 만큼인 512MB, GC 가 필요에 따라 늘리거나 줄입니다 |
| RSS | 그중 물리 프레임이 매핑되어 RAM 에 올라와 있는 부분 | 실제로 접근한 페이지만큼 |

committed 와 RSS 의 차이가 2절의 구분과 같습니다. JVM 이 512MB 를 commit 해도 Linux 는 그 범위를 주소 공간에 추가할 뿐이고, 프레임은 JVM 이 각 페이지에 처음 쓸 때 준비합니다. 아직 객체를 하나도 두지 않은 힙 영역은 committed 에 포함되지만 RSS 에는 포함되지 않습니다.

이 표는 힙만 다룬 단순화입니다. JVM 프로세스에는 Metaspace, thread stack, code cache, GC 자료 구조, 네이티브 라이브러리도 있고, 이 영역들도 각자 reserved 와 committed 를 가집니다. 또 GC 가 committed 를 줄이며 운영체제에 반환한 페이지는 RSS 에서도 빠지지만, 반환하지 않고 남겨 둔 빈 영역은 RSS 에 계속 남습니다. 그래서 committed 와 RSS 의 크기 관계는 시점에 따라 달라지고 한쪽이 항상 다른 쪽에 포함되지는 않습니다.

## 6. JVM 에서 직접 확인하려면 어떻게 할까요?

Enter 를 누를 때마다 100MB 배열을 하나씩 만들어 붙잡아 두는 프로그램입니다.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Scanner;

public class MemoryExperiment {

    private static final List<byte[]> allocations = new ArrayList<>();

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        System.out.println("PID: " + ProcessHandle.current().pid());

        while (true) {
            System.out.println("Enter: Allocate 100MB");
            scanner.nextLine();

            byte[] data = new byte[100 * 1024 * 1024];

            // 각 4KB 구간에 실제 쓰기 수행
            for (int i = 0; i < data.length; i += 4096) {
                data[i] = 1;
            }

            allocations.add(data);

            Runtime runtime = Runtime.getRuntime();
            System.out.println("Total Heap: " + runtime.totalMemory() / 1024 / 1024 + "MB");
            System.out.println("Used Heap: "
                    + (runtime.totalMemory() - runtime.freeMemory()) / 1024 / 1024 + "MB");
        }
    }
}
```

Linux 에서 NMT(Native Memory Tracking)를 켜고 실행하면 reserved 와 committed 를 JVM 에게서 직접 받을 수 있습니다.

```bash
javac MemoryExperiment.java
java -Xms512m -Xmx2g -XX:NativeMemoryTracking=summary MemoryExperiment
```

다른 터미널에서 세 단계를 각각 읽습니다.

```bash
# reserved 와 committed: Java Heap 항목
jcmd <PID> VM.native_memory summary

# VSZ 와 RSS, 그리고 지금까지의 minor/major page fault 횟수
ps -o pid,vsz,rss,min_flt,maj_flt,comm -p <PID>

# 매핑별 값을 합친 Rss, Pss, Private_Dirty
cat /proc/<PID>/smaps_rollup
```

동작 원리에서 추론한 예상은 다음과 같습니다.

- 시작 직후 NMT 의 Java Heap 은 reserved 2GB, committed 512MB 로 나오고 RSS 는 512MB 보다 훨씬 작을 것입니다.
- Enter 를 누를 때마다 RSS 가 100MB 가까이 늘고 `min_flt` 가 크게 늘 것입니다. 100MB 를 4KB 페이지로 나누면 25,600 페이지입니다.
- `Used Heap` 이 512MB 를 넘으면 `Total Heap` 과 committed 가 늘어날 것입니다.

이 실험은 Linux 의 demand zeroing 만 따로 재는 실험이 아닙니다. Java 는 새 배열의 원소가 모두 0이어야 하므로 HotSpot 이 배열을 만들 때 그 메모리를 직접 0으로 채웁니다. 그래서 코드의 4KB 간격 쓰기 루프가 없어도 `new byte[]` 에서 이미 모든 페이지에 쓰기가 일어납니다. 운영체제가 0으로 채운 페이지를 JVM 이 한 번 더 0으로 채우는 것입니다. 또 GC 가 배열을 어느 영역에 둘지, 언제 힙을 늘릴지에 따라 숫자가 달라집니다. 이 실험으로 확인할 수 있는 것은 JVM 이 commit 한 크기와 Linux 가 RAM 에 올린 크기가 따로 움직인다는 사실까지입니다. 정확한 수치는 JDK 버전, GC 종류, 커널 설정에 따라 달라집니다.

## 7. `AlwaysPreTouch` 는 무엇을 앞당길까요?

HotSpot 에는 demand zeroing 을 일부러 피하는 옵션이 있습니다.

```bash
-XX:+AlwaysPreTouch
```

Oracle 문서는 이 옵션을 운영체제에서 힙을 받은 뒤, 애플리케이션에 메모리를 내주기 전에 힙의 모든 페이지에 접근하도록 VM 에 요청하는 옵션으로 설명합니다. 기본값은 꺼져 있고, 이때는 애플리케이션이 힙을 쓰면서 페이지가 하나씩 준비됩니다. 켜면 4절의 page fault 와 0 채우기를 JVM 시작 단계에서 한꺼번에 치릅니다.

미리 접근하는 범위는 JVM 이 그 시점에 commit 한 힙입니다. `-Xmx` 전체를 미리 접근하지는 않습니다. `-Xms512m -Xmx2g` 라면 시작할 때 512MB 가 대상이고 나머지는 힙이 늘어날 때 다룹니다. 두 실행을 같은 조건에서 비교하려면 초기 크기와 최대 크기를 같게 둡니다.

```bash
java -Xms1g -Xmx1g MemoryExperiment

java -Xms1g -Xmx1g -XX:+AlwaysPreTouch MemoryExperiment
```

두 실행에서 비교할 값은 다음과 같습니다.

1. `PID:` 가 출력될 때까지 걸린 시간
2. 시작 직후의 RSS 와 `min_flt`
3. 첫 번째 100MB 할당에 걸린 시간과 그동안 늘어난 `min_flt`

예상대로라면 `AlwaysPreTouch` 를 켠 쪽은 시작이 늦고 시작 직후 RSS 가 1GB 가까이 됩니다. 대신 이후 할당에서 늘어나는 page fault 가 거의 없습니다. 끈 쪽은 바로 시작하지만 힙을 처음 쓰는 구간마다 page fault 비용을 냅니다.

같은 비용을 언제 낼지 고르는 선택입니다. 첫 요청부터 지연이 고르게 나와야 하는 서비스나, 힙을 결국 다 쓰게 되는 서비스라면 시작 시간을 늘려서라도 미리 접근하는 쪽이 유리할 수 있습니다. 반대로 시작 속도가 중요하거나 힙을 다 쓰지 않는 서비스는 lazy 방식으로 RAM 을 아낍니다.

## 8. `fork()` 는 부모 메모리를 전부 복사할까요?

`fork()` 는 호출한 프로세스를 복제해 자식 프로세스를 만듭니다.

```c
pid_t pid = fork();
```

자식은 부모와 똑같은 주소 공간을 받습니다. 부모가 1GB 를 쓰고 있었다면 자식도 같은 주소에서 같은 1GB 를 봐야 합니다. 그렇다고 `fork()` 할 때마다 1GB 를 복사하면 시간도 오래 걸리고 RAM 도 두 배로 필요합니다. 부모와 자식이 그 메모리를 읽기만 한다면 복사한 1GB 는 원본과 똑같은 내용으로 남습니다.

OSTEP 은 이 문제를 copy-on-write 로 설명합니다. 이 아이디어는 적어도 TENEX 운영체제까지 거슬러 올라갑니다. 운영체제가 한 주소 공간의 페이지를 다른 주소 공간으로 복사해야 할 때, 복사하는 대신 같은 물리 페이지를 대상 주소 공간에도 매핑하고 양쪽 모두 읽기 전용으로 표시합니다. 양쪽이 읽기만 하면 데이터를 한 바이트도 옮기지 않고 복사가 끝납니다.

## 9. copy-on-write 는 어떻게 동작할까요?

`fork()` 직전에는 부모의 가상 페이지 A 가 물리 프레임 10 에 매핑되어 있습니다.

```text
Parent: Virtual Page A ---> Physical Frame 10 [ Hello ]
```

`fork()` 직후에는 부모와 자식의 페이지 A 가 모두 프레임 10 을 가리키고, 두 PTE 모두 쓰기가 막혀 있습니다.

```text
Parent: Virtual Page A ---+
                          +---> Physical Frame 10 [ Hello ]  (read-only)
Child:  Virtual Page A ---+
```

이제 자식이 이 페이지에 씁니다.

```c
data[0] = 'Y';
```

1. 쓰기가 막힌 페이지에 쓰려고 했으므로 page fault 가 일어나 운영체제로 트랩합니다.
2. 운영체제는 이 페이지가 COW 페이지인지 확인합니다.
3. 맞으면 새 프레임을 할당하고 프레임 10 의 내용을 복사한 뒤, 자식의 페이지 A 를 새 프레임에 쓰기 가능하게 매핑합니다.
4. 트랩에서 돌아와 자식이 쓰기를 다시 실행합니다. 이번에는 자기 프레임에 씁니다.

```text
Parent: Virtual Page A ---> Physical Frame 10 [ Hello ]
Child:  Virtual Page A ---> Physical Frame 20 [ Yello ]
```

복사는 쓰기가 일어난 페이지에서, 쓰기가 일어난 순간에만 합니다. 1GB 중 자식이 4KB 페이지 열 개에 썼다면 복사되는 양은 40KB 입니다. 부모 쪽 프레임 10 은 이제 부모만 매핑하고 있으므로, Linux 는 다음에 부모가 이 페이지에 쓸 때 복사하지 않고 쓰기 권한만 되돌려 줍니다.

## 10. page fault 는 항상 디스크를 읽을까요?

[swap 을 다룬 글](/blog/ostep-swap-oom-linux-container/)에서는 present bit 가 0인 페이지에 접근하면 page fault 가 나고, handler 가 swap space 에서 페이지를 읽어 온다고 정리했습니다. 그 흐름만 보면 page fault 는 곧 디스크 I/O 처럼 보입니다.

demand zeroing 과 COW 도 page fault 로 동작하지만 디스크를 읽지 않습니다. demand zeroing 은 RAM 의 빈 프레임을 0으로 채우고, COW 는 RAM 에 있는 프레임을 RAM 의 새 프레임으로 복사합니다. COW 에서는 페이지가 RAM 에 있는데도 PTE 가 쓰기를 막고 있어서 page fault 가 납니다.

| 상황 | page fault 가 나는 이유 | 운영체제의 처리 | 디스크 I/O |
|---|---|---|---|
| swap 된 페이지 접근 | 페이지가 RAM 에 없습니다 | swap space 에서 읽어 옵니다 | 있음 |
| demand-zero 페이지 첫 접근 | 아직 프레임이 매핑되지 않았습니다 | 0으로 채운 프레임을 매핑합니다 | 없음 |
| COW 페이지에 쓰기 | 공유 중인 페이지라 쓰기가 막혀 있습니다 | 내용을 복사한 새 프레임을 매핑합니다 | 없음 |
| 주소 공간 밖 접근 | 프로세스가 쓸 수 없는 주소입니다 | `SIGSEGV` 로 프로세스를 종료합니다 | 없음 |

Linux 는 디스크 I/O 없이 처리한 page fault 를 minor fault, I/O 가 필요했던 page fault 를 major fault 로 따로 셉니다. 6절에서 `ps` 로 읽은 `min_flt` 와 `maj_flt` 가 이 두 값입니다. JVM 이 힙을 처음 쓰는 구간에서 page fault 가 많이 늘어도 대부분 `min_flt` 쪽이라면 swap 이나 파일 I/O 와는 상관없습니다. page fault 는 운영체제가 개입해야 하는 메모리 접근이 있었다는 신호이고, 그 자체로 오류는 아닙니다.

## 11. `fork()` 이후 메모리는 어떻게 바뀔까요?

Linux 에서 COW 를 확인하는 Python 프로그램입니다. Java 의 `ProcessBuilder` 는 자식 프로세스에서 곧바로 다른 프로그램을 실행하므로 부모의 메모리를 그대로 들고 있는 자식을 만들기 어렵습니다. Python 은 `os.fork()` 로 시스템 콜을 그대로 호출할 수 있습니다.

```python
import os
import time

SIZE = 100 * 1024 * 1024

data = bytearray(SIZE)

# 실제 물리 페이지에 쓰기 발생
for i in range(0, SIZE, 4096):
    data[i] = 1

print(f"Parent PID: {os.getpid()}", flush=True)

pid = os.fork()

if pid == 0:
    print(f"Child PID: {os.getpid()}", flush=True)

    print("Before COW", flush=True)
    time.sleep(15)

    # 자식 프로세스에서 각 페이지 수정
    for i in range(0, SIZE, 4096):
        data[i] = 2

    print("After COW", flush=True)
    time.sleep(60)

else:
    os.waitpid(pid, 0)
```

`Before COW` 가 출력된 뒤 15초 안에 한 번, `After COW` 가 출력된 뒤 한 번 두 프로세스의 값을 읽습니다.

```bash
cat /proc/<PARENT_PID>/smaps_rollup
cat /proc/<CHILD_PID>/smaps_rollup
```

`smaps_rollup` 은 프로세스의 모든 매핑에 대한 `smaps` 값을 합친 파일입니다. 이 실험에서 비교할 값은 셋입니다.

- **Rss**: 이 프로세스에 매핑되어 RAM 에 올라와 있는 크기입니다. 다른 프로세스와 공유하는 페이지도 그대로 들어가므로 부모와 자식의 RSS 를 더하면 공유 페이지를 두 번 셉니다.
- **Pss**: 공유 페이지를 공유하는 프로세스 수로 나눠 센 크기입니다. [커널 문서](https://docs.kernel.org/filesystems/proc.html)의 예로, 혼자 쓰는 페이지 1,000개와 다른 프로세스 하나와 공유하는 페이지 1,000개가 있으면 PSS 는 1,500 페이지입니다.
- **Private_Dirty**: 이 프로세스만 매핑하고 있고 수정된 페이지의 크기입니다. 커널은 한 번만 매핑된 페이지를 private, 여러 번 매핑된 페이지를 shared 로 셉니다.

<CowForkFrames />

동작 원리에서 추론한 예상은 다음과 같습니다.

| 시점 | 부모 | 자식 |
|---|---|---|
| `fork()` 직후 | Rss 에 배열 100MB 가 들어가고, 그 100MB 는 Shared_Dirty 로 셉니다. Pss 에는 그 절반이 들어갑니다 | 부모와 같습니다 |
| 자식이 모든 페이지에 쓴 뒤 | 쓰지 않았는데도 배열 100MB 가 Private_Dirty 로 옮겨 가고 Pss 가 늘어납니다 | 새로 복사한 100MB 가 Private_Dirty 로 늘어납니다 |

자식이 COW 로 자기 프레임을 받아 가면 원래 프레임은 부모만 매핑하게 되므로, 부모는 아무것도 쓰지 않았는데 Private_Dirty 가 늘어납니다. 두 프로세스의 Rss 는 처음부터 100MB 를 포함하고 있었으므로 크게 변하지 않을 것입니다. 메모리가 실제로 두 배가 된 사실은 Rss 합계에서는 드러나지 않고 Pss 합계와 Private_Dirty 에서 드러납니다.

Python 인터프리터 자체의 메모리도 함께 측정되고, 자식이 Python 객체를 건드리면 reference count 가 바뀌면서 객체가 있던 페이지도 COW 로 복사됩니다. 그래서 정확히 100MB 만큼 변하지는 않습니다. Pss 와 Private_Dirty 가 움직이는 방향을 비교하면 주소 공간은 `fork()` 순간 복제되고 물리 페이지는 쓰기가 일어난 만큼만 복제된다는 것을 확인할 수 있습니다.

## 12. `fork()` 와 `exec()` 에서 COW 는 무엇을 아낄까요?

OSTEP 은 UNIX 계열에서 COW 가 특히 중요한 이유로 `fork()` 와 `exec()` 의 조합을 듭니다.

```c
pid_t pid = fork();

if (pid == 0) {
    execl("/bin/ls", "ls", NULL);
}
```

자식은 `fork()` 로 부모의 주소 공간을 받은 직후 `exec()` 를 호출합니다. `exec()` 는 지금 주소 공간을 버리고 새 프로그램의 주소 공간으로 바꿉니다. `fork()` 가 부모의 메모리를 실제로 모두 복사했다면 그 데이터는 거의 쓰이지 않은 채 바로 버려집니다.

COW 를 쓰면 `fork()` 는 부모의 물리 페이지를 공유하도록 매핑만 하고, `exec()` 는 그 매핑을 해제한 뒤 새 프로그램의 주소 공간을 만듭니다. 자식이 `exec()` 전에 쓴 몇 페이지, 예를 들어 스택 페이지 정도만 복사됩니다.

COW 를 써도 `fork()` 의 비용이 0이 되지는 않습니다. [fork(2) man page](https://man7.org/linux/man-pages/man2/fork.2.html)는 Linux 의 `fork()` 가 copy-on-write 페이지로 구현되어 있어서, 남는 비용은 부모의 페이지 테이블을 복제하는 시간과 메모리, 자식의 task 구조를 만드는 일뿐이라고 설명합니다. 부모가 쓰는 메모리가 클수록 페이지 테이블도 커지므로 이 비용도 커집니다. OSTEP 은 공유 라이브러리를 여러 프로세스의 주소 공간에 COW 로 매핑해 메모리를 아끼는 것도 COW 의 쓰임으로 듭니다.

## 13. Java 백엔드에서는 어디서 이 차이를 만날까요?

Java 개발자가 페이지 테이블을 직접 다룰 일은 없습니다. 하지만 JVM 도 Linux 위의 프로세스이므로 JVM 의 메모리 지표는 지금까지 정리한 동작을 따릅니다.

Spring Boot 애플리케이션을 메모리 한도 512MB 인 컨테이너에서 `-Xmx400m` 으로 실행한다고 가정합니다.

```bash
docker run --memory=512m my-spring-app
java -Xmx400m -jar app.jar
```

힙 상한이 400MB 이니 512MB 안에 들어갈 것 같지만, JVM 프로세스는 힙 밖에서도 Metaspace, thread stack, code cache, direct buffer, 네이티브 라이브러리의 메모리를 씁니다. cgroup 은 이 메모리를 모두 컨테이너 사용량에 포함합니다. 힙 밖 메모리가 컨테이너를 종료시킨 사례는 [Java 힙은 여유로운데 컨테이너는 왜 종료될까?](/blog/ostep-java-native-memory-container-oom/)에서 다뤘습니다.

여기에 이 글의 두 기법이 더해지면 다음 현상을 설명할 수 있습니다.

- **시작 직후에는 문제가 없다가 부하가 몰리면 메모리 한도에 걸리는 경우**: demand zeroing 때문에 `-Xms` 나 `-Xmx` 를 크게 잡아도 처음에는 RSS 가 작습니다. 힙을 실제로 채우는 시점이 와야 RSS 가 커지고 cgroup 사용량도 그때 늘어납니다. `AlwaysPreTouch` 와 `-Xms` 를 `-Xmx` 와 같게 두면 이 시점을 시작 단계로 당겨서, 한도가 부족한지를 배포 직후에 알 수 있습니다.
- **여러 프로세스의 RSS 합이 RAM 보다 큰 경우**: `fork()` 로 만든 worker 들이나 같은 공유 라이브러리를 쓰는 프로세스들은 물리 페이지를 공유합니다. RSS 를 더하면 그 페이지를 여러 번 세므로 실제 사용량은 PSS 합계로 계산해야 합니다. cgroup v2 는 메모리 영역을 처음 만든 cgroup 에 그 메모리를 포함하므로, 한 cgroup 안에서 공유하는 페이지는 사용량에 한 번만 들어갑니다. 참고: [Control Group v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).
- **새로 띄운 인스턴스의 첫 요청들이 느린 경우**: JIT 컴파일과 클래스 로딩 외에도, 힙과 thread stack 을 처음 쓰는 페이지마다 minor fault 가 납니다. `min_flt` 가 시작 직후에 몰려 늘어나는지 확인하면 이 비용이 얼마나 되는지 가늠할 수 있습니다.

다만 컨테이너가 OOMKilled 로 종료되는 이유를 두 기법만으로 설명할 수는 없습니다. 실제 원인을 찾으려면 NMT 로 JVM 영역별 committed 를 읽고, cgroup 의 `memory.current` 와 `memory.stat` 으로 컨테이너가 어떤 종류의 메모리를 쓰는지 나누고, Linux 의 메모리 회수와 OOM 정책을 확인해야 합니다. swap 과 OOM 의 관계는 [swap 을 다룬 글](/blog/ostep-swap-oom-linux-container/)에 정리했습니다.

| 미루는 동안의 상태 | PTE 에 접근할 수 없다고 표시하고 프레임은 없습니다 | 두 주소 공간이 같은 프레임을 읽기 전용으로 매핑합니다 |
| 작업을 하는 시점 | 그 페이지에 처음 접근할 때 | 그 페이지에 처음 쓸 때 |
| 운영체제가 알게 되는 방법 | page fault 후 PTE 의 운영체제용 비트 | page fault 후 COW 페이지 여부 |
| 끝내 하지 않아도 되는 경우 | 할당만 하고 접근하지 않은 페이지 | 읽기만 한 페이지, `exec()` 로 버려진 주소 공간 |
| Linux 와 JVM 에서 만나는 곳 | committed 힙과 RSS 의 차이, `AlwaysPreTouch` | `fork()` 비용, RSS 합계와 PSS 합계의 차이 |

운영체제가 작업을 미룰 수 있는 이유는 프로세스가 가상 주소로만 메모리를 쓰기 때문입니다. 프로세스는 주소 공간에 페이지가 있다는 것만 알고, 그 뒤에 프레임이 있는지, 다른 프로세스와 공유 중인지는 모릅니다. 운영체제는 PTE 의 접근 권한으로 첫 접근이나 첫 쓰기를 page fault 로 받아서, 그때 필요한 작업만 합니다.

미룬 작업의 비용은 첫 접근의 지연으로 돌아옵니다. 페이지마다 minor fault 를 처리하고, 0으로 채우거나 복사하는 시간이 그 접근에 더해집니다. 힙을 결국 다 쓰는 서비스라면 lazy 방식은 비용을 없애지 못하고 요청 처리 중으로 옮길 뿐이고, 이럴 때는 `AlwaysPreTouch` 로 비용을 시작 단계에 몰아서 낼 수 있습니다. 어느 쪽이 나은지는 서비스가 시작 시간과 첫 요청의 지연 중 무엇을 더 중요하게 여기는지에 따라 다릅니다.

직접 실행해 확인하고 싶은 질문도 남았습니다.

- 6절의 JVM 실험에서 NMT 의 committed 와 RSS, `min_flt` 는 100MB 할당마다 예상대로 움직일까요?
- `-Xms1g -Xmx1g` 에서 `AlwaysPreTouch` 를 켜면 시작 시간은 얼마나 늘고, 첫 100MB 할당의 지연은 얼마나 줄까요?
