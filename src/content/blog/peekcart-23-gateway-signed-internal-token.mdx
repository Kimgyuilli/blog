## 관문 뒤의 서비스는 헤더를 그대로 믿고 있었습니다

게이트웨이를 앞에 세운 직후, PeekCart의 인증은 이렇게 흘러갔습니다.

- 사용자 토큰은 게이트웨이가 한 번만 검증합니다.
- 검증에 성공하면 게이트웨이는 바깥에서 들어온 `X-User-*` 헤더를 지우고, 검증한 값으로 `X-User-Id` · `X-User-Role` · `X-User-Family-Id`를 다시 넣어 서비스로 넘깁니다.
- 다섯 서비스는 이 헤더를 **검증 없이** 믿습니다.
- 서비스로 곧장 가는 길은 두 겹으로 막았습니다. 서비스는 클러스터 내부 주소(ClusterIP)로만 열었고, NetworkPolicy는 게이트웨이 Pod와 Prometheus만 8080 포트로 들어오게 했습니다.

서비스 쪽 필터의 주석이 이 신뢰를 그대로 적고 있었습니다.

```java
/**
 * Gateway 가 검증 후 주입한 신뢰 헤더(X-User-Id/X-User-Role/X-User-Family-Id)로
 * 인증을 세우는 필터. 서명 검증은 하지 않는다 — Gateway 가 이미 검증했고,
 * 외부 유입 헤더는 Gateway 가 strip 후 재주입하며, 직접 경로는 NetworkPolicy 로 차단된다.
 */

```

### 헤더가 진짜라는 보장은 어디서 왔을까요?

이 구조에서 헤더를 믿어도 되는 이유는 하나입니다. 게이트웨이 말고는 서비스에 닿을 수 없다는 것입니다. 그리고 그 사실을 지키는 것은 NetworkPolicy 하나입니다.

담이 사라져도 서비스는 그것을 알 수 없습니다. 정책이 강제되지 않든, 라벨이 어긋나 정책이 엉뚱한 Pod를 고르든, 서비스는 똑같이 헤더를 믿습니다. 담이 멀쩡해도 빈틈은 남습니다. 정책은 게이트웨이 Pod를 들여보내도록 열려 있으니, 그 Pod 안에서 보낸 요청은 담을 그대로 통과합니다. 그런 위치를 얻은 공격자라면 요청 하나로 충분합니다.

```bash
# 예시: 정책이 강제되지 않을 때의 아무 Pod, 또는 정책이 허용한 게이트웨이 Pod 에서 보내는 요청
curl -X POST http://product-service:8080/api/v1/admin/products \
  -H 'X-User-Id: 1' -H 'X-User-Role: ADMIN' \
  -H 'Content-Type: application/json' -d '{...}'
```

상품 관리 API는 `hasRole('ADMIN')`으로 보호돼 있지만, 서비스가 보기에 이 요청은 1번 관리자가 보낸 것입니다. 로그인도 토큰도 필요 없습니다. 이 curl은 설명을 위해 만든 예시이고 실제로 보낸 기록은 없습니다. `X-User-Role: ADMIN`이 `ROLE_ADMIN` 권한이 된다는 필터 단위 테스트와 `@PreAuthorize` 설정에서 끌어낸 결론입니다. 가장 가까운 실측은 뒤에서 다룹니다.

### 아직 굳지 않은 상태였습니다

이 구조는 머지됐지만, 서명을 결정한 시점까지 실제 클러스터에 올라간 적은 없었습니다. 외부 입구가 닫혔는지, NetworkPolicy가 정말 강제되는지, 위조 헤더가 막히는지를 보는 보안 smoke가 남아 있었고, 이것을 통과하기 전에는 다음 단계로 넘어가지 않기로 했습니다. 다음 단계로 가는 문이 "NetworkPolicy가 실제로 강제되는가"에 걸려 있었다는 것은, 그만큼 이 정책이 인증을 떠받치고 있는데도 아직 한 번도 확인되지 않았다는 뜻이기도 했습니다.

원래 계획한 다음 단계는 게이트웨이가 서비스로 함께 넘기던 원래 토큰(`Authorization`)을 끊고, 서비스에 남은 옛 토큰 검증기를 지우는 것이었습니다. 그러고 나면 평문 헤더가 유일한 인증 근거로 굳습니다. 평문 신뢰가 아직 클러스터에 올라가지 않았으니, 굳히기 전이라면 신뢰의 근거를 바꿀 수 있었습니다.

그래서 질문은 둘이었습니다. 네트워크 격리 한 겹에 기대던 신뢰를 무엇으로 받칠까요? 그리고 새로 세운 방어가 실제로 막는다는 것은 어떻게 보일 수 있을까요?

## 어떻게 접근할 수 있을까요?

### 담과 서명은 막는 것이 다릅니다

네트워크 격리와 서명 검증은 서로 다른 질문에 답합니다. **네트워크 격리**는 "누가 서비스에 닿을 수 있는가"를 정하고, **서명 검증**은 "이 신원은 누가 보증한 것인가"를 확인합니다.

| 갖춘 것 | 막는 것 | 뚫리는 것 |
| --- | --- | --- |
| 담(NetworkPolicy)만 | 바깥이나 다른 Pod에서 서비스를 직접 두드리는 요청 | 담이 무너지거나 허용된 Pod 안이라면 헤더 한 줄로 아무 신원이나 만들 수 있습니다 |
| 서명만 | 위조한 신원. 개인키 없이는 유효한 신원을 만들 수 없습니다 | 아무 Pod나 서비스에 닿습니다. 인증이 필요 없는 경로는 그대로 열리고, 쏟아지는 요청도 막지 못합니다 |
| 둘 다 | 신원을 위조하려면 담과 개인키를 **함께** 뚫어야 합니다 | |

당시는 첫 줄이었습니다. 담을 하나 더 세워도 이 구조는 바뀌지 않으니, 필요한 것은 신원 자체를 증명하는 두 번째 겹이었습니다. 담을 치울 이유도 없습니다. 담은 인증 없는 직접 요청과 공격 표면을 줄이는 일을 계속합니다.

### 신원을 증명하는 방법은 여럿입니다

검토한 방법은 지금 구조를 유지하는 것을 포함해 다섯 가지였습니다.

| 방법 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 평문 헤더 유지 | 추가 작업이 없고 지연도 가장 낮습니다 | 신뢰가 여전히 담 하나에 걸립니다 |
| 공유 비밀(HMAC)로 헤더 서명 | 대칭키라 빠르고, 비밀 하나만 배포하면 됩니다 | 모든 서비스가 서명 비밀을 가져야 합니다. 서비스 하나만 뚫려도 누구의 신원이든 만들 수 있습니다 |
| 서비스 메시의 mTLS | "이 요청은 진짜 게이트웨이가 보냈다"를 전송 계층에서 증명합니다 | 사이드카와 컨트롤 플레인을 새로 들여야 합니다 |
| 원래 사용자 토큰을 넘기고 서비스마다 다시 검증 | 신뢰 헤더라는 개념이 필요 없습니다 | 검증 로직이 다섯 번 중복되고, 서비스마다 차단 목록을 Redis에서 다시 조회합니다. 게이트웨이로 모으며 없앤 바로 그것입니다 |
| **게이트웨이가 개인키로 서명한 내부 토큰** | 서명은 게이트웨이만 할 수 있고, 서비스는 공개키로 검증만 합니다 | 서비스마다 요청당 RSA 검증 한 번이 늘고, 게이트웨이가 관리할 개인키가 하나 생깁니다 |

공유 비밀과 비대칭 서명은 비슷해 보이지만 피해 반경이 다릅니다. 공유 비밀에서는 검증하는 쪽이 곧 서명할 수 있는 쪽입니다. 비대칭 서명에서는 서비스가 뚫려도 공개키만 나가므로, 위조할 수 있는 곳이 게이트웨이 하나로 줄어듭니다. mTLS는 이 단계의 범위에 비해 컸습니다. 서명한 내부 토큰만으로 메시 없이 위조 방어의 핵심을 얻을 수 있어서, mTLS는 이후 후보로 남겼습니다.

### 내부 토큰은 이렇게 생겼습니다

게이트웨이는 사용자 토큰 검증에 성공하면 평문 헤더 대신 `X-Internal-Auth` 헤더 하나를 넣습니다. 값은 게이트웨이 개인키로 서명한 짧은 JWT입니다.

| 항목 | 값 |
| --- | --- |
| 알고리즘 | RS256만 허용 |
| 발행자(`iss`) | `peekcart-gateway` |
| 신원 | `sub`(사용자 ID), `role`(USER · ADMIN), `fid`(refresh token family) |
| 수명 | 게이트웨이는 30초로 발행합니다. 서비스는 수명이 120초를 넘는 토큰을 거부하고, 시계 오차는 5초까지만 봐줍니다 |
| 키 | 사용자 토큰 서명키와 다른, 게이트웨이 전용 키 쌍 |

이름들은 설정으로 바꿀 수 없게 코드 상수로 고정했습니다. 발행자 이름이 환경마다 달라질 수 있다면, "누가 발행했는가"라는 신뢰의 기준을 설정 하나로 우회할 수 있기 때문입니다.

```java
public static final String HEADER = "X-Internal-Auth";
/** 내부 토큰의 유일한 발행자. 검증측은 이 값으로 iss 를 핀한다(사용자 access token 오용 차단). */
public static final String ISSUER = "peekcart-gateway";
/** 서명 알고리즘. 검증측은 이 값만 허용한다(alg 혼동/HS fallback 차단). */
public static final String ALGORITHM = "RS256";
```

서비스는 서명만 보지 않고 **발행자와 키 ID(`kid`)까지 게이트웨이 것으로 고정**합니다. 사용자 access token도 진짜 서명이 붙은 RS256 JWT이기 때문입니다. 서명만 확인한다면 사용자 토큰이 내부 토큰 자리에 들어와도 통과하고, 게이트웨이를 거치지 않은 토큰이 인증 근거가 됩니다.

로그아웃 확인과 탈취 차단은 게이트웨이에 그대로 둡니다. 서비스는 30초짜리 토큰의 서명만 확인하면 되니 Redis를 다시 조회할 필요가 없습니다. 공개키 로딩과 JWT 파싱 코드는 사용자 토큰 검증을 위해 만들어 둔 것을 대부분 다시 썼습니다.

### 평문은 건너뛰고 곧장 서명으로 갑니다

평문 신뢰가 아직 클러스터에 올라가지 않았으니, 평문을 먼저 배포하고 나중에 바꿀 이유가 없었습니다. 다만 무중단 전환을 가정하면 서비스가 평문과 서명을 **둘 다** 받는 구간이 잠깐 필요합니다. 그래서 순서를 이렇게 정했습니다.

1. 실제 클러스터에서 NetworkPolicy가 강제되는지부터 확인합니다. 확인되지 않으면 여기서 멈춥니다.
2. 서비스가 평문과 서명 토큰을 둘 다 받게 배포합니다.
3. 게이트웨이가 서명 토큰을 넣게 배포합니다.
4. 서비스가 서명 토큰만 받게 바꿉니다.
5. 위조 토큰과 평문 헤더가 막히는지 다시 확인합니다.
6. 게이트웨이가 넘기던 원래 토큰을 끊고, 서비스의 옛 검증기를 지웁니다.

1번이 맨 앞인 이유는 2번 때문입니다. 2번 구간의 서비스는 평문을 받으므로, 그때 담이 실제로 서 있지 않다면 평문 위조가 그대로 통하는 창이 열립니다. 각 단계는 전체 Pod가 새 상태로 바뀐 것을 확인한 뒤에야 넘어갑니다.

방향은 정해졌지만, 이 계획은 결정 기록과 계획서 위에서 세운 것이었습니다.

## 해 보려니 이런 문제가 있었습니다

### 계획의 전제가 코드와 달랐습니다

코드를 쓰기 전에 계획이 기대는 사실을 현재 코드로 다시 확인했더니 세 가지가 달랐습니다.

| 계획의 전제 | 코드에서 확인한 사실 | 바뀐 것 |
| --- | --- | --- |
| 서비스의 옛 토큰 검증 필터가 살아 있어, 전환 중간에 사용자 토큰으로 게이트웨이를 우회할 수 있다 | 다섯 서비스 모두 이미 헤더 신뢰 필터만 썼고, 옛 필터는 어디에도 연결되지 않은 죽은 코드였습니다 | 계획이 가장 심각하게 다룬 위험이 성립하지 않았습니다. 옛 검증기 삭제는 롤아웃 순서와 무관한 정리 작업이 됐습니다 |
| 롤백하려면 옛 검증기와 새 필터를 함께 담은 전용 이미지가 필요하다 | 같은 이유로 불필요했습니다 | 되돌릴 대상은 직전 릴리스 이미지입니다 |
| user-service 개인키를 클러스터에 배포하는 매니페스트가 있다 | **아예 없었습니다.** 앞선 GKE 세션은 임시 k8s Secret으로 때웠습니다 | 키 배포를 정본화하는 범위에 사용자 토큰 개인키도 넣었습니다 |

결정 기록에서 그대로 쓸 수 없는 줄도 있었습니다. 결정 기록은 게이트웨이 공개키를 서비스가 원래 쓰던 공개키 목록(`app.jwt.rs256.public-keys`)에 추가하자고 적었는데, user-service는 그 목록을 JWKS 엔드포인트로 **통째로** 게시합니다.

```java
@GetMapping("/.well-known/jwks.json")
public Map<String, List<Map<String, String>>> jwks() {
    List<Map<String, String>> keys = publicKeyRegistry.all().entrySet().stream()
```

그대로 따랐다면 내부 신뢰의 기준인 게이트웨이 공개키가 외부 공개 엔드포인트에 실렸을 것입니다.

### 발행하는 쪽과 검증하는 쪽이 서로를 볼 수 없었습니다

내부 토큰은 게이트웨이가 만들고 공용 인증 모듈이 검증합니다. 그런데 게이트웨이는 WebFlux, 공용 인증 모듈은 servlet 기반이라 서로 의존할 수 없습니다. 의존하는 순간 게이트웨이에 servlet이 딸려 들어와 부팅이 깨집니다. 그러면 헤더·발행자·claim 이름을 양쪽에 각각 문자열로 적어야 하고, 한쪽만 바뀌면 둘이 조용히 어긋납니다. 두 모듈을 한 테스트에서 함께 띄워 확인할 수도 없었습니다.

### 클러스터가 없으면 검사할 대상도 없었습니다

새 게이트웨이는 개인키 파일이 없으면 부팅을 거부합니다. 그 개인키는 Secret Manager에서 CSI 드라이버로 마운트할 예정이었으니, 이 인프라가 준비되기 전에는 매니페스트를 만들어도 실제로 뜰 수 없었습니다. 그리고 그때 클러스터는 0개였습니다. 앞선 GKE 세션을 마치며 모두 지웠기 때문입니다.

순서도 문제였습니다. "개인키는 소유한 워크로드 하나만 마운트한다"를 검사하는 lint를 매니페스트보다 먼저 짜면, 검사할 대상이 없어 **늘 통과**합니다. 아무것도 확인하지 않는 녹색(vacuous-green)입니다. 검사가 통과했다는 것과 검사가 일했다는 것은 다릅니다.

롤아웃 계획의 전제도 흔들렸습니다. 클러스터가 비어 있으니 옮겨 갈 옛 이미지도, 흐르는 트래픽도 없었습니다. 여섯 단계는 무중단 전환이 아니라, 빈 클러스터 위에서 그 절차를 일부러 재현하는 **리허설**이 될 수밖에 없었습니다.

### 규정은 있는데, 규정이 가리키는 주체가 없었습니다

키 배포 매니페스트를 만들고 한 달 뒤, 클러스터 세션을 계획하며 같은 방식으로 착수 전 확인을 돌렸더니 하나가 더 나왔습니다. 개인키를 마운트하는 `SecretProviderClass`의 주석과 lint는 이렇게 규정하고 있었습니다.

```yaml
#   - `nodePublishSecretRef` 금지 — 노드 인증은 Workload Identity 로 한다(정적 자격증명 금지).
```

Workload Identity는 Pod의 k8s ServiceAccount를 GCP 서비스 계정에 묶어, 그 신원으로 Secret Manager에 접근하게 하는 방식입니다. 그런데 `k8s/` 전체에 `kind: ServiceAccount`는 **0건**, `serviceAccountName`도 **0건**이었습니다. 모든 Pod가 네임스페이스의 `default` 계정으로 뜨고 있었습니다.

이대로 클러스터에 갔다면 둘 중 하나였습니다. 결선이 없으니 CSI가 키를 가져오지 못해 게이트웨이가 뜨지 않고, 클러스터를 켠 뒤 고치는 시간이 곧 비용이 됩니다. 아니면 급한 대로 `default` 계정에 권한을 줘서, 그 네임스페이스의 **모든 Pod**가 서명 개인키를 꺼낼 수 있게 됩니다.

기존 검사가 이것을 잡지 못한 이유도 있었습니다. 키 소유 lint는 "개인키 볼륨을 누가 마운트하는가"를 꼼꼼히 봤지만, Secret Manager 접근 권한은 **볼륨이 아니라 신원**에 붙습니다. 권한 있는 계정으로 뜬 Pod는 볼륨 없이도 `gcloud secrets versions access`로 키를 읽을 수 있습니다. 볼륨만 보는 검사에는 걸리지 않는 경로입니다.

### 검증 도구가 먼저 틀렸습니다

막는 장치를 만들면서 그것이 막는다는 것을 확인하는 도구도 함께 만들었습니다. 리뷰에서 찾은 결함 중 상당수가 그 도구 쪽에 있었습니다.

| 도구 | 결함 | 결과 |
| --- | --- | --- |
| "서비스에 사용자 토큰을 직접 보내면 거부된다" 테스트 | 처음부터 깨진 문자열을 토큰으로 보냈습니다 | 옛 검증기가 되살아나도 통과합니다 |
| 부팅 시 필터 구성 검사 | 보안 필터 체인이 0개면 검사 없이 넘어갔습니다 | 체인이 사라진 상태를 통과시킵니다 |
| 키 도메인 분리 검사 | 테스트용 키 하나만 대조했습니다 | 다른 키가 섞여도 통과합니다 |
| 개인키 마운트 승인 lint | `SecretProviderClass`를 이름으로만 승인했습니다 | 이름은 두고 가리키는 키만 바꾸는 우회가 열립니다 |
| 키 소유자 판정 | 워크로드를 이름으로만 봤습니다 | `Job/gateway`가 게이트웨이로 통과합니다 |
| 개인키 파일 탐지 | 파일 이름 정규식으로 찾았습니다 | `bundle.pem`에 넣은 개인키를 놓칩니다 |
| 롤아웃 수렴 게이트 | 내부 python 블록이 이스케이프 문제로 파싱조차 되지 않았습니다 | 클러스터가 없어 한 번도 실행되지 않았고, 실제 세션 첫 실행에서 터졌을 코드였습니다 |

판단이 틀린 곳도 있었습니다. "게이트웨이에 요청해 200이 나오면 서명 토큰을 넣고 있다"는 판정은 서비스가 서명만 받을 때만 참입니다. 평문도 받는 전환 구간에서는 평문을 넣어도 200입니다.

여기까지 오면 질문이 바뀝니다. 서명 토큰을 만드는 것보다, 클러스터 없이 확인할 수 있는 것과 없는 것을 가르고 각 검사가 정말 일한다는 것을 보이는 쪽이 더 큰 일이었습니다.

## 좀 더 적절한 해결책은 무엇일까요?

### "클러스터 없이 녹색이 되는가"로 나눴습니다

한 PR로 묶으면 코드는 CSI 인프라를 기다려야 하고, lint를 먼저 짜면 검사할 대상이 없습니다. 그래서 작업을 **클러스터 없이 끝까지 녹색이 될 수 있는가**로 나눴습니다.

| 조각 | 담은 것 | 클러스터 없이 확인한 것 | 일부러 남긴 것 |
| --- | --- | --- | --- |
| 코드 | 내부 토큰 발행·검증, 옛 검증기 삭제 | 10개 모듈 빌드·테스트, 키 도메인 lint | 게이트웨이 매니페스트는 개인키 마운트가 없어 배포할 수 없음 |
| 매니페스트·lint·스크립트 | 개인키 CSI 마운트, 공개키 ConfigMap, 키 소유 lint, 롤아웃 게이트, smoke 확장 | 렌더, lint 녹색, 일부러 틀린 입력에서 lint가 빨간색이 되는지 | Secret Manager에 키가 없어 실제 적용 불가 |
| 클러스터 증적 | 실제 키 주입, 롤아웃 리허설, 위조 차단 실측 | 없음. 이 조각만 클러스터에서 합니다 | |

조각마다 같은 원칙을 적었습니다. **렌더가 녹색인 것을 배포 가능으로 기록하지 않는다.** 확인하지 못한 것은 확인하지 못했다고 남기고 다음 조각의 진입 조건으로 넘깁니다. 매니페스트를 먼저 만들고 lint를 그 뒤에 붙이는 순서도 계획에 못박았습니다.

Workload Identity 결선은 원래 클러스터 증적 조각의 일이 아니었습니다. 하지만 클러스터 없이 끝나는 일이고, 클러스터를 켠 채 고치면 그 시간이 비용입니다. 그래서 경계를 깬다는 사유를 계획에 적고, 클러스터를 켜기 전에 별도 PR로 먼저 냈습니다.

리허설도 생략하지 않았습니다. 옮길 트래픽이 없으니 건너뛸 수도 있었지만, 그러면 전환 절차와 수렴 판정과 롤백 행렬이 한 번도 실행되지 않은 문서로 남습니다. 평문과 서명을 함께 받는 모드가 실제로 동작하는지도 모른 채 그 모드를 지우게 됩니다. 대신 증적에는 "무중단 전환을 실증했다"가 아니라 "그 절차를 빈 클러스터 위에서 재현했다"고 적기로 했습니다.

### 키는 이름이 아니라 지문으로, 이름은 한 곳에만

게이트웨이 공개키는 사용자 토큰 공개키 목록에 넣지 않고 전용 목록(`app.internal-token.public-keys`)에 따로 둡니다. "둘이 섞이지 않았다"는 키 ID로 비교하면 같은 키를 다른 ID로 넣는 순간 빠져나갑니다. 그래서 공개키 DER 인코딩의 SHA-256 지문으로 비교했습니다. 같은 키라면 어떤 ID와 포맷으로 들어와도 지문이 같습니다. 이 검사는 lint와 다섯 서비스 통합 테스트 양쪽에 걸었고, 테스트용 키 하나만 대조하던 검사는 **두 목록의 지문 집합이 서로 겹치지 않는가**로 바꿨습니다.

게이트웨이와 공용 인증 모듈이 서로를 볼 수 없는 문제는 둘 다 볼 수 있는 제3의 모듈로 풀었습니다. 헤더·발행자·claim 이름만 담은, 프레임워크 의존이 없는 순수 Java 모듈(`internal-token-contract`)입니다. 게이트웨이가 servlet 계열 모듈을 의존하지 못하게 막는 빌드 가드에는 이 모듈 하나를 예외로 열고, 예외가 뒷문이 되지 않도록 **이 모듈 자신이 다른 프로젝트 모듈이나 Spring을 의존하면 실패하는** 검사를 함께 넣었습니다. 두 모듈을 한 테스트에서 띄울 수 없는 문제는, 계약대로 서명한 토큰을 공용 테스트 fixture로 커밋하고 양쪽이 각자 그 토큰으로 테스트하게 해서 풀었습니다. 한쪽만 바뀌면 반대쪽 테스트가 깨집니다.

### 개인키는 etcd를 거치지 않게 했습니다

k8s Secret은 etcd에 base64로 저장될 뿐이라, `kubectl get secret` 권한만 있으면 원문이 나옵니다. 내부 토큰 개인키는 담이 뚫렸을 때 남는 마지막 방어선이고, 새어 나가면 모든 서비스에 대한 위조가 가능해집니다.

그래서 개인키는 Secret Manager에 두고, CSI 드라이버가 노드의 메모리 파일시스템(tmpfs)으로 직접 투영하게 했습니다. 받은 비밀을 k8s Secret으로 다시 만들어 주는 옵션(`secretObjects`)과 정적 자격증명 옵션(`nodePublishSecretRef`)은 이 이점을 되돌리므로 lint가 금지합니다. 사용자 토큰 개인키도 같은 방식으로 옮겼습니다.

공개키는 비밀이 아니지만 이미지에 굽지 않고 ConfigMap에 뒀습니다. 회전 중에는 공개키 목록이 1개 → 2개 → 1개로 바뀌는데, 이미지에 고정하면 회전이 빌드 파이프라인에 묶입니다. ConfigMap 편집과 재시작만으로 끝나야 "공개키 먼저 배포 → 전체 반영 확인 → 서명키 전환" 순서를 지킬 수 있습니다.

### 볼륨이 아니라 신원을 검사했습니다

개인키를 쓰는 워크로드는 게이트웨이와 user-service 둘입니다. 각자 전용 ServiceAccount를 만들고 **서로 다른** GCP 서비스 계정에 묶었으며, 각 GCP 계정에는 자기 비밀 하나의 읽기 권한만 줬습니다. 한 계정에 두 비밀 권한을 몰아주면 CSI 마운트가 나뉘어 있어도 신원 층위에서 교차 접근이 열리고, 그것은 렌더 결과에 보이지 않습니다.

키 소유 lint에는 신원 검사 두 개를 더했습니다. 키를 소유한 워크로드가 전용 ServiceAccount를 쓰고 그 계정이 승인된 GCP 계정에 정확히 묶였는지, 그리고 그 ServiceAccount를 다른 워크로드가 빌려 쓰지 않는지입니다. 두 번째 검사가 일한다는 것은 일부러 틀린 입력 하나로 보였습니다. **볼륨을 하나도 마운트하지 않고** 게이트웨이의 ServiceAccount만 빌려 쓰는 Job입니다. 기존 볼륨 검사는 모두 녹색이고 새 검사만 빨간색이 됩니다.

### 음성 검사에는 양성 대조를 붙였습니다

"막혔다"는 검사는 막을 대상이 처음부터 없어도 통과합니다. 이 함정은 서명 작업에 들어가기 전, 미뤄 둔 GKE 보안 smoke를 서명 도입 전 상태로 돌릴 때 먼저 드러났습니다.

검사 하나는 "서비스로 가는 직접 경로 5개가 모두 도달 불가"였습니다. 그런데 새로 만든 클러스터에는 직접 경로가 처음부터 없습니다. 게다가 로드밸런서가 모두 내부용이라 VPC 밖에서 돌리면 어떤 주소를 넣어도 응답이 없습니다. 그대로 돌렸다면 아무것도 확인하지 않고 통과했을 검사입니다. 그래서 세 상태를 차례로 측정했습니다. 직접 경로는 앞서 지운 서비스 노출 설정을 git에서 복원해 실제로 띄웠고, smoke는 VPC 안의 VM에서 돌렸습니다.

| 상태 | 직접 경로 | NetworkPolicy | 결과 |
| --- | --- | --- | --- |
| ① | 있음 | 없음 | **200**. 검사가 도달을 감지할 수 있다는 양성 대조 |
| ② | 있음 | 있음 | 000. NetworkPolicy 하나의 효과 |
| ③ | 없음(ClusterIP) | 있음 | 000. 노출 자체를 없앤 상태 |

①에서 ③으로 곧장 가면 노출 제거와 정책 적용이 한꺼번에 일어나, 무엇이 차단을 만들었는지 가를 수 없습니다. 그래서 ②를 끼웠습니다. 이 smoke는 barrier 5개와 canary 3개를 모두 통과했고, 롤아웃 1단계("NetworkPolicy가 실제로 강제되는가")의 조건을 채웠습니다.

이후 모든 검사에 같은 원칙을 적용했습니다. **음성 검사 옆에는 그 검사가 통과를 감지할 수 있다는 양성 대조를 둡니다.**

- 위조 토큰이 401이라는 barrier에는 **정상 서명 토큰이 200**이라는 대조를 함께 둡니다. 전부 거부하는 고장 난 상태가 통과로 보이지 않게 하기 위해서입니다.
- "사용자 토큰을 서비스에 직접 보내면 거부된다" 테스트는 진짜 유효한 사용자 토큰을 보내고, 서비스 쪽에는 그 토큰의 검증키를 **일부러 등록**해 둡니다. 옛 검증기가 되살아나면 테스트가 실제로 깨집니다.
- 양성 대조는 "401이 아니다"가 아니라 405 · 200 · 404처럼 구체적인 상태로 고정합니다. "401이 아니다"는 403이나 5xx도 통과시킵니다.
- lint의 자기 시험은 "오류 ID가 나왔는가"가 아니라 **오류 ID별 기대 횟수**로 판정합니다. 틀린 입력 변형은 35종에서 49종으로 늘었습니다.
- 서명 주입 판정은 먼저 서비스가 서명만 받는 상태인지 확인하고, 아니면 판정을 거부합니다.

## 최종적으로 이렇게 됐습니다

### 담과 서명이 각각 무엇을 막는지 실제 클러스터에서 봤습니다

클러스터 증적은 NetworkPolicy를 강제하는 Dataplane V2와 Workload Identity를 켠 GKE 클러스터에서 두 번의 세션으로 확보했습니다. 시작할 때 클러스터는 비어 있었으므로, 이 세션은 운영 중 전환이 아니라 **빈 클러스터 위의 리허설**입니다. 증적 첫머리에도 그렇게 적었습니다.

먼저 담을 다시 확인했습니다. 세 상태 측정을 그대로 돌렸고, 직접 경로 5개가 ①에서 모두 200, ②와 ③에서 모두 000이었습니다. 게이트웨이가 아닌 Pod에서 서비스로 가는 요청도 막혔습니다.

다음은 서명입니다. 서비스가 서명 토큰만 받는 상태에서 네 가지를 보냈습니다.

| 보낸 것 | 결과 | 의미 |
| --- | --- | --- |
| 아무 키로나 서명한 위조 `X-Internal-Auth` | 401 | 게이트웨이 개인키 없이는 신원을 만들 수 없습니다 |
| 평문 `X-User-*` | 401 | 평문 헤더는 더 이상 신원이 아닙니다 |
| 정상 로그인 토큰 | **200** | 양성 대조. 위의 401이 "전부 거부"가 아니라는 증거입니다 |
| 게이트웨이 Pod 안에서 서비스로 직접 보낸 **유효한** 사용자 토큰 | 401 | 서비스에 사용자 토큰 검증기가 남아 있지 않습니다 |

처음에 담이 멀쩡해도 허용된 게이트웨이 Pod 안에서는 헤더를 넣을 수 있다고 했습니다. 이 경로도 측정됐습니다. 원래는 "서명만 받는 모드에서 평문도 받는 모드로 되돌리는 롤백이 동작하는가"를 보려던 측정입니다. 게이트웨이를 거쳐 평문을 보내면 게이트웨이가 바깥 헤더를 항상 지우므로 모드와 상관없이 401이 나옵니다. 그래서 관측 지점을 게이트웨이 Pod 안으로 옮겼습니다.

| 서비스 모드 | 게이트웨이 Pod → order-service, 평문 `X-User-*` |
| --- | --- |
| 서명만 받음 | 401 |
| 평문도 받음(환경 변수 하나로 전환) | **200** |
| 다시 서명만 받음 | 401 |

세 번 모두 order-service 이미지 digest는 같았습니다. 평문을 믿는 서비스라면 허용된 Pod 하나가 곧 위조 경로가 되고, 서명만 받는 서비스에서는 그 경로가 닫힙니다. 다만 이것은 셸에서 평문 헤더를 보낸 측정입니다. 게이트웨이 Pod를 장악해 개인키까지 읽는 경우는 이 측정이 다루지 않습니다.

개인키가 etcd를 거치지 않는다는 것도 확인했습니다. 게이트웨이 Pod 안의 키 파일은 읽기 전용이었고, 네임스페이스의 모든 k8s Secret에서 `PRIVATE KEY` 문자열은 0건이었습니다. 앞선 smoke에서 사용자 토큰 개인키를 임시 k8s Secret으로 때웠던 편차도 이로써 정리됐습니다.

Workload Identity 결선은 권한을 빼 보는 것으로 확인했습니다. GCP 계정에서 비밀 읽기 권한을 빼자 게이트웨이 Pod는 `PermissionDenied`와 함께 `ContainerCreating`에 멈췄고, 권한을 돌려주자 다시 떴습니다. 여기에도 함정이 있었습니다. 권한을 뺀 **직후** 배포한 Pod는 정상으로 떴습니다. IAM 권한 변경이 전파되는 데 시간이 걸렸기 때문입니다. Pod를 지워 새로 마운트하게 하자 그제야 막혔습니다. 그대로 결론을 냈다면 "권한을 뺐는데도 뜬다, 이 결선은 의미가 없다"고 잘못 기록했을 것입니다.

### 실제로 돌려 보니 계획이 틀린 곳이 있었습니다

키를 실제로 넣자마자 하나가 깨졌습니다. 개인키는 Secret Manager의 새 키로 바뀌었는데, 공개키는 이미지에 구운 개발용 키 그대로였습니다. 서명은 되는데 검증이 안 되는 상태입니다. barrier는 이것을 잡지 못했습니다. 공개 경로의 200만 확인했고, "토큰 없이 보호 경로에 가면 401"은 키가 깨져도 똑같이 401이기 때문입니다. **토큰을 들고 보호 경로에 가면 200**이라는 양성 대조를 돌리고서야 드러났습니다.

내부 토큰 쪽은 공개키를 ConfigMap으로 바꿔 끼울 자리가 있었지만 사용자 토큰 쪽에는 없었습니다. 첫 세션은 개발용 키 쌍을 Secret Manager에 올려 우회했고, "사용자 토큰을 운영 전용 키로 돌렸다"는 것은 증명하지 못한 채 남겼습니다. 같은 세션은 `kubectl apply -k`를 할 때마다 게이트웨이 replica가 HPA 최소값 아래로 깎이는 결함도 찾았습니다. 두 결함을 별도 PR로 고친 뒤, 두 번째 세션에서는 두 키 도메인 모두 운영 전용 키로 돌렸습니다.

리허설의 출발점도 손으로 만들어야 했습니다. 빈 클러스터에 배포하니 커밋 기본값대로 곧장 "서명만 받음" 상태에 도착했습니다. 그래서 거꾸로 되감았습니다. 먼저 다섯 서비스를 "평문도 받음"으로 올리고, 그다음 게이트웨이를 서명 도입 전 이미지로 내렸습니다. 순서를 바꾸면 서명만 받는 서비스가 평문을 거부해 모든 요청이 401이 됩니다. 현재 이미지에 평문 주입을 잠시 되살리는 방법은 쓰지 않았습니다. 증적을 위해 지운 공격 표면을 되살리는 셈이기 때문입니다.

### 키를 바꿔 보니 롤백 문서가 틀려 있었습니다

두 번째 세션에서는 내부 토큰 서명키를 실제로 회전했습니다.

| 단계 | 결과 |
| --- | --- |
| ① 새 공개키를 먼저 배포(옛 키 유지) | ConfigMap에 키 쌍 추가 |
| ② 다섯 서비스 반영 확인 | 모든 서비스가 두 kid를 함께 받음 |
| ③ 개인키와 `active-kid` 전환 | 로그인 200, 보호 경로 200. 끊김 없음 |
| ④ 옛 토큰 수명 경과 대기 | 80초(수명 30초 + 시계 오차 5초 + 여유) |
| ⑤ 옛 키 제거 | 옛 kid가 실제로 사라짐 |

⑤에서 옛 kid가 "사라졌다"는 데 의미가 있습니다. 착수 전에는 Spring이 설정 목록을 항목별로 합친다고 생각했는데, 테스트해 보니 우선순위가 가장 높은 소스가 목록을 **통째로** 대체했습니다. 그래서 ConfigMap이 신뢰할 kid 목록의 유일한 출처가 되고, 키를 빼면 실제로 폐기됩니다. 클러스터에서도 그대로였습니다.

다음으로 금지된 순서를 일부러 재현했습니다. 새 공개키를 배포하지 않고 게이트웨이부터 새 키로 바꿨습니다.

- 실패는 "전 요청 401"로 시작하지 않았습니다. 옛 Pod와 새 Pod가 섞인 동안은 `401 200 200`처럼 **일부만** 실패했고, 모든 Pod가 바뀐 뒤에야 전면 401이 됐습니다.
- 롤아웃 게이트는 이 상태를 "반영 완료"로 통과시켰습니다. 이미지·replica·옛 ReplicaSet 정리가 모두 정상이었기 때문입니다. 막은 것은 Pod마다 실제로 요청을 보내 보는 서명 probe 단계 하나였습니다.

되돌리는 쪽에서 더 큰 문제가 나왔습니다. `active-kid`를 옛 값으로 되돌렸는데 401이 그대로였습니다. Secret Manager의 `versions/latest`가 여전히 새 개인키를 가리키고 있어서, **새 키로 서명하고 옛 kid를 붙인** 토큰이 흐르고 있었습니다. kid와 개인키는 짝이라 둘 다 되돌려야 합니다. 그래서 새 키 버전을 비활성화했더니 더 나빠졌습니다.

```
FailedPrecondition desc = Secret Version [.../versions/3] is in DISABLED state.
```

`versions/latest`는 비활성 버전을 건너뛰지 않습니다. 401이던 것이 Pod가 아예 뜨지 못하는 상태로 악화됐고, 옛 키를 **새 버전으로 다시 올리자** 복구됐습니다. 같은 회전 기전을 쓰는 사용자 토큰 runbook은 이 경우 "`active-kid`를 옛 kid로 되돌리고 롤링하면 바로 복구된다"고 적고 있었습니다. 틀린 문서였고, 이 실측을 근거로 같은 PR에서 고쳤습니다.

### 사용자 토큰 회전은 로컬에서 축 하나만 확인했습니다

여기까지 회전한 것은 내부 토큰입니다. 사용자 토큰은 키를 배우는 경로가 다릅니다.

| | 내부 토큰 | 사용자 토큰 |
| --- | --- | --- |
| 공개키를 쓰는 쪽 | 다섯 서비스 | 게이트웨이 하나 |
| 키를 배우는 경로 | ConfigMap, 부팅할 때 | user-service의 JWKS를 HTTP로 조회. 모르는 kid를 만난 순간 |

게이트웨이는 JWKS를 user-service **Service**로 조회합니다. 회전 중에 그 조회가 아직 새 키를 모르는 옛 Pod로 가면, 정상적인 새 토큰도 401이 됩니다. runbook은 이 위험을 적고, 회전 전에 모든 Pod의 JWKS를 Pod IP로 직접 확인하는 게이트를 두라고 했습니다. 다만 둘 다 실제로 확인한 적은 없었습니다.

{/* 데모 후보 위치: JWKS 조회가 닿는 Pod에 따라 같은 kid 토큰이 401/200으로 갈리는 장면. 구현 여부는 작성자 결정 대기. */}

이 축은 클라우드가 아니라 k8s Service 동작의 문제이고, Secret Manager와 Workload Identity 쪽은 두 번째 세션이 이미 확인했습니다. 그래서 이 확인은 minikube에서 했고, 사용자 토큰 개인키는 k8s Secret으로 대신 넣었습니다. 그러니 이 드릴의 결론은 "사용자 토큰 회전을 운영 환경에서 완주했다"가 아니라 **"그 축 하나를 실증했다"**까지입니다.

첫 시도는 실패했습니다. 금지된 순서로 회전하며 1초 간격으로 요청했는데 401이 나오지 않았습니다. 게이트웨이 로그를 보니 첫 새 토큰이 발급된 순간 이미 모든 Pod가 새 키를 알고 있었습니다. 한 번의 표본으로 판정할 수 없는 경쟁 상태라, 상태를 고정해 결정적으로 재현하는 쪽으로 바꿨습니다.

옛 키만 아는 Pod 3개와 새 키도 아는 Pod 1개를 고정해 두고, 게이트웨이를 다섯 번 재시작하며 121번 로그인했습니다. **121번 모두 옛 키 Pod가 응답했고, 새 Pod는 한 번도 맞히지 않았습니다.** 요청마다 무작위로 분배된다면 이럴 확률은 0.75^121, 약 10^-15입니다. 같은 Service를 요청마다 새 커넥션으로 부르면 20번 중 7번이 새 Pod로 갔습니다. 게이트웨이는 커넥션을 재사용하므로 한 번 물린 Pod에 고정됩니다. runbook의 "어느 Pod가 응답할지 보장되지 않는다"보다 나쁜 동작입니다.

- 한 번 옛 Pod에 물리면 계속 그 Pod로 갑니다. JWKS 재조회 대기(10초) 뒤 다시 시도해도 같은 커넥션이라 저절로 낫지 않습니다.
- 새 Pod에 물린 게이트웨이 인스턴스는 끝까지 정상입니다. 그래서 일부 사용자만 401을 봅니다. "전 요청 401"을 장애 신호로 기다리면 놓칩니다.

경쟁 상태를 없애려고 로그인 경로와 JWKS 경로를 각각 Pod IP로 고정하고, JWKS를 응답하는 Pod만 바꿨습니다.

| | 로그인 | JWKS 조회 | 결과 |
| --- | --- | --- | --- |
| D1 | 새 Pod | **옛** Pod | 새 kid 토큰 401 × 10/10 |
| D2 | 새 Pod | 새 Pod | 새 kid 토큰 200 × 10/10 |

토큰의 kid는 양쪽이 같습니다. 바뀐 것은 JWKS를 응답한 Pod 하나뿐이니 401의 원인은 그 Pod입니다. 같은 상태에서 runbook의 사전 확인 게이트를 돌리자, 옛 kid만 가진 Pod 3개를 그대로 짚으며 차단했습니다. 정상 순서로 회전했을 때는 전환 구간 내내 1초 간격으로 보낸 요청 79번 가운데 401이 0건이었습니다.

### 규정은 있는데 주체가 없던 곳이 하나 더 있었습니다

관측성 계약에는 "인증 실패를 게이트웨이와 user-service에서 센다"는 행이 5월부터 있었지만, 게이트웨이 코드에는 메트릭 계측이 0건이었습니다. 게이트웨이가 요청을 거부해도 그 사유를 셀 수 없는 상태로 PR 네 개를 지나왔습니다. 마무리 PR에서 거부 사유별 카운터를 넣었습니다. 응답은 `invalid_token` 하나로 합쳐 내보내고, 서명 오류·만료·허용되지 않은 알고리즘 같은 세부 사유는 메트릭에서만 나눕니다. 세부 사유를 응답에 실으면 위조를 시도하는 쪽에 피드백을 주기 때문입니다. 두 번째 세션에서 위조 토큰을 넣어 카운터가 실제로 오르는지 확인했고, 정상 트래픽 31,873건에서 인증 실패는 0건이었습니다.

인증 경로 비용은 경로 전체로만 쟀습니다. 한도 아래 부하(경로당 15 req/s)에서 인증 경로 p95는 23.61ms, 공개 경로는 13.67ms였습니다. 이 9.9ms 차이에는 서명 외에 JWT 파싱·Redis 차단 조회·다운스트림 홉이 모두 들어 있어서, 서명 하나의 비용으로 읽을 수 없습니다.

## 더 좋은 방법은 없었을까요?

여기부터는 작업을 마친 뒤 돌아본 분석입니다. 당시 이 관점들을 대안으로 검토한 기록은 없고, 이후의 실측과 외부 자료에 비춰 다시 본 것입니다.

### 서명은 "누가 보냈나"를 증명하지만 "누구에게 보냈나"는 증명하지 않습니다

내부 토큰에는 `sub`·`role`·`fid`·`iss`·`iat`·`exp`가 들어 있습니다. 받을 서비스를 적는 `aud`와 토큰마다 고유한 ID인 `jti`는 없습니다. 그래서 클러스터 안에서 `X-Internal-Auth` 하나를 가로채면, 유효 기간 안에는 다섯 서비스 어디로든 다시 보낼 수 있습니다. 그 창은 발행 수명 30초에 서비스가 봐주는 시계 오차 5초를 더해 최대 약 35초입니다. 게이트웨이에서 서비스로 가는 구간은 평문 HTTP입니다. 예를 들어 order-service로 가던 관리자 요청의 토큰을 가로채면, 그 35초 동안 상품 관리 API에도 관리자로 들어갈 수 있습니다. 이것은 claim 구성과 검증 규칙에서 도출한 시나리오이고, 실행해 보지는 않았습니다.

JWT 모범 사례인 [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)는 이 공격에 이름을 붙여 둡니다.

> "There are attacks in which one recipient will be given a JWT that was intended for it and will attempt to use it at a different recipient for which that JWT was not intended." (§2.7 Substitution Attacks)
>
> 자기에게 발행된 JWT를 받은 수신자가, 그 JWT가 의도하지 않은 다른 수신자에게 그것을 쓰려는 공격이 있습니다.

> "If the same issuer can issue JWTs that are intended for use by more than one relying party or application, the JWT MUST contain an "aud" (audience) claim …" (§3.9)
>
> 같은 발행자가 둘 이상의 신뢰 당사자나 애플리케이션을 위한 JWT를 발행할 수 있다면, JWT는 의도한 당사자가 쓰는지 판별할 수 있는 `aud` claim을 반드시 담아야 합니다.

PeekCart의 내부 토큰이 바로 그 조건입니다. 발행자는 게이트웨이 하나이고 받는 쪽은 다섯 서비스입니다. 게이트웨이는 라우트마다 어느 서비스로 보내는지 알고 있으니, 그 이름을 `aud`로 넣고 서비스가 자기 이름과 대조하게 할 수 있었다고 봅니다. 그러면 가로챈 토큰은 원래 가던 서비스에서만 쓸 수 있습니다. 같은 서비스로 다시 보내는 것까지 막으려면 `jti`를 기억하는 저장소가 필요한데, 그러면 서비스에서 Redis 조회를 없앤 이점을 되돌리게 됩니다. 보내는 쪽 자체를 묶는 것은 보류한 mTLS의 몫입니다.

다만 이 공격은 이미 클러스터 안에서 트래픽을 엿볼 수 있는 위치를 전제로 합니다. 서명이 막으려던 위협(헤더를 직접 지어내는 것)보다 한 단계 깊은 위치입니다. 이 위협을 얼마나 무겁게 볼지 판단한 기록은 없습니다.

### 허용된 Pod 자체가 뚫리면 개인키도 함께 나갑니다

서명으로 닫은 것은 "담 안이나 허용된 Pod에서 헤더를 지어내는" 경로입니다. 게이트웨이 Pod 자체를 손에 넣으면 사정이 다릅니다. 개인키가 파일로 마운트돼 있으니 읽어 갈 수 있고, 읽어 간 키로는 Pod 밖에서도 키를 회전할 때까지 언제든 서명할 수 있습니다.

키 저장을 결정할 때 이 방향의 대안이 이미 있었습니다. Cloud KMS의 비대칭 서명입니다. [Cloud KMS 문서](https://docs.cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys.cryptoKeyVersions)는 이렇게 적습니다.

> "For security reasons, the raw cryptographic key material represented by a `CryptoKeyVersion` can never be viewed or exported."
>
> 보안상의 이유로, `CryptoKeyVersion`이 나타내는 원시 키 재료는 조회하거나 내보낼 수 없습니다.

현재 구조에 KMS를 대입해 보면, 탈취한 Pod에서 서명 API를 부를 수는 있어도 키를 들고 나갈 수는 없으니 Pod를 잃는 순간 서명 능력도 잃습니다. 대가도 분명합니다. 게이트웨이는 **요청마다** 내부 토큰을 새로 서명하므로, KMS로 옮기면 요청마다 KMS 호출이 붙고 인증 경로가 그 API의 지연과 가용성에 묶입니다. 캐싱 같은 변형은 따져 보지 않았습니다. 결정 기록도 이 점 때문에 KMS를 "서명 지연을 측정한 뒤 판단"으로 미뤘습니다. 측정값은 이후 생겼지만(로컬 서명 p95 1.80ms, 클러스터 인증 경로 차이 +9.9ms), 이 값으로 KMS 여부를 판단한 기록은 남아 있지 않습니다.

같은 눈으로 보면 처음의 Prometheus 경로도 다시 보입니다. 도메인 서비스는 관리용 엔드포인트를 업무 API와 같은 8080 포트에 두고, NetworkPolicy는 Prometheus에 8080을 열어 둡니다. 구성만 보면 평문 신뢰 시절에는 Prometheus Pod도 업무 API에 헤더를 넣을 수 있는 위치였고, 서명 이후에는 이 경로로 할 수 있는 일이 "인증 없이 공개 API를 부르는 것"으로 줄어듭니다. 이 경로를 위조 경로로 따로 분석하거나 측정한 기록은 없습니다.

### 클러스터에서 찾은 결함 중 무엇을 더 일찍 잡을 수 있었을까요?

GKE 세션이 찾은 결함을 "클러스터 없이 잡을 수 있었는가"로 다시 나눠 봤습니다. 첫 줄 외에는 실행해 보지 않은 판단입니다.

| 결함 | 클러스터 없이 | 근거 |
| --- | --- | --- |
| `apply -k`가 게이트웨이 replica를 HPA 최소값 아래로 깎음 | **가능** | 렌더 결과에 `replicas: 1`과 `minReplicas: 2`가 함께 보이고, 동작은 k8s 일반 동작입니다(아래 실험) |
| 공개키를 배포하지 않고 개인키만 바꿈 | 가능했을 것 | 새 키로 한 번만 돌리면 드러나는 계획 누락입니다. 다만 당시 로컬에서는 CSI 없이 게이트웨이가 뜨지 못했습니다 |
| `versions/latest`가 비활성 버전을 건너뛰지 않음 | GKE 없이, GCP만으로 | Secret Manager 자체의 동작입니다 |
| IAM 권한 변경 전파 지연 | 불가 | GCP IAM 고유 동작입니다 |

첫 줄이 정말 클러스터와 무관한지 이 글을 쓰면서 확인했습니다. 별도 minikube profile(minikube v1.38.1, k8s v1.35.1)에 nginx Deployment 두 개와 HPA(`minReplicas: 2`)를 띄웠습니다. A는 `replicas: 1`을 선언하고, B는 `replicas`를 선언하지 않았습니다. metrics-server는 없었지만 HPA는 "현재 replica가 최소값보다 적다"는 사유로 둘 다 2로 올렸습니다. 그 상태에서 두 매니페스트를 다시 apply하기를 세 번 반복했습니다.

| 회차 | A (`replicas: 1` 선언) | B (선언 없음) |
| --- | --- | --- |
| 1 | apply 직후 1, 약 12초 뒤 HPA가 2로 복구 | `unchanged`, 2 유지 |
| 2 | apply 직후 1, 약 4~6초 뒤 2 | `unchanged`, 2 유지 |
| 3 | apply 직후 1, 약 10초 뒤 2 | `unchanged`, 2 유지 |

A에서는 apply할 때마다 실행 중이던 Pod 하나가 실제로 내려갔습니다(ready 1). 결함 직전 커밋의 GKE overlay를 렌더해 보니 HPA 대상인 `gateway`가 `spec.replicas=1`, `minReplicas=2`로 그대로 나왔습니다. 렌더 단계의 lint 하나로 잡을 수 있었던 결함이고, 실제로 이 결함을 고칠 때 그런 lint를 함께 넣었습니다. 이 실험은 PeekCart 매니페스트가 아니라 같은 조합을 흉내 낸 최소 구성이고, 복구 시간은 HPA 동기화 주기와 노드 여유에 따라 달라질 수 있습니다.

돌아보면 "클러스터 없이 녹색이 되는가"는 **어디서 검사를 돌릴 수 있는가**로 작업을 나눴습니다. 그런데 클러스터에서 처음 드러난 결함 중 일부는 렌더만으로도 보이는 것이었고, 그 조합을 검사하는 lint가 없었을 뿐입니다. 또 개인키를 CSI로만 받게 한 설계 때문에 로컬에서 게이트웨이를 띄울 수 없었고, 로컬 리허설이라는 중간 단계도 처음부터 없었습니다. 사용자 토큰 드릴은 나중에 k8s Secret으로 대체한 전용 overlay로 그 단계를 열었습니다. 같은 overlay가 클러스터 세션 전에 있었다면 공개키 누락은 GKE를 켜기 전에 드러났을 가능성이 크다고 봅니다.

### 표준 패턴과는 무엇이 같고 무엇이 다를까요?

"관문이 바깥 토큰을 검증하고, 안쪽용 토큰을 새로 만들어 넘긴다"는 구조에는 알려진 선례가 있습니다. [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)(OAuth 2.0 Token Exchange) §1은 리소스 서버가 받은 액세스 토큰을 백엔드 호출에 맞는 새 토큰으로 바꾸는 사용을 예로 듭니다.

> "An OAuth resource server, for example, might assume the role of the client during token exchange in order to trade an access token that it received in a protected resource request for a new token that is appropriate to include in a call to a backend service." (§1)

Curity가 정리한 [phantom token 패턴](https://curity.io/resources/learn/phantom-token-pattern/)은 게이트웨이 쪽에 더 가깝습니다. 클라이언트는 불투명한 참조 토큰만 들고 있고, 게이트웨이가 그것을 JWT로 바꿔 넘깁니다.

> "The reverse proxy replaces the by-reference token with the by-value token in the actual request to the microservice."
>
> 리버스 프록시는 마이크로서비스로 가는 실제 요청에서 참조 토큰을 값 토큰으로 바꿔 넣습니다.

| | RFC 8693 | phantom token | PeekCart |
| --- | --- | --- | --- |
| 클라이언트가 가진 것 | 액세스 토큰 | 불투명한 참조 토큰 | 사용자 JWT |
| 안쪽 토큰을 만드는 곳 | 별도 토큰 서비스(STS) | 토큰 서비스. 게이트웨이는 조회만 합니다 | **게이트웨이가 직접 서명** |
| 받을 곳 지정 | `audience`·`resource` 파라미터 | 글에서 다루지 않음 | 없음 |

같은 점은 안쪽 토큰이 바깥에 나가지 않는다는 것입니다. PeekCart 게이트웨이도 바깥에서 들어온 `X-Internal-Auth`를 항상 지웁니다. 가장 큰 차이는 **누가 안쪽 토큰을 만드느냐**입니다. PeekCart는 토큰 서비스를 한 번 더 부르지 않고 게이트웨이가 직접 서명합니다. 홉이 하나 줄었지만, 그 대가로 게이트웨이가 서명 개인키를 들고 있게 됐습니다. 앞의 "게이트웨이 Pod가 뚫리면" 문제는 이 선택에서 나옵니다. RFC 8693이 `audience`를 요청 파라미터로 둔 것도 앞의 재전송 문제와 같은 축입니다.

표준이 권하는 것을 이미 따른 부분도 있습니다. RFC 8725 §3.12는 한 시스템이 여러 종류의 JWT를 쓸 때 서로 섞이지 않게 검증 규칙을 나누라고 하고, 그 방법의 하나로 이것을 듭니다.

> "Use different keys for different kinds of JWTs. Then the keys used to validate one kind of JWT will fail to validate other kinds of JWTs."
>
> 종류가 다른 JWT에는 다른 키를 쓰십시오. 그러면 한 종류를 검증하는 키로는 다른 종류의 JWT를 검증할 수 없습니다.

사용자 토큰과 내부 토큰을 다른 키로 서명하고, 발행자를 고정하고, 두 공개키 목록이 지문 단위로 겹치지 않게 강제한 것이 이 권고와 맞습니다.

## 정리하며

평문 헤더를 믿던 구조에서 신뢰를 지탱한 것은 NetworkPolicy 하나였습니다. 서명한 내부 토큰을 더하자 신원을 위조하려면 담과 게이트웨이 개인키를 함께 뚫어야 하게 됐습니다. 빈 클러스터 위의 리허설에서 이것을 확인했습니다. 위조 토큰과 평문 헤더는 401, 정상 토큰은 200이었고, 담이 허용한 게이트웨이 Pod 안에서도 서명만 받는 서비스에는 평문이 통하지 않았습니다.

막는 장치를 만드는 것만큼 품이 든 것은 그 장치가 일한다는 것을 보이는 일이었습니다. 검사할 대상이 없는 lint, 무엇이든 통과하는 테스트, 권한 전파를 기다리지 않은 음성 대조가 차례로 녹색을 거짓으로 만들 뻔했고, 그때마다 양성 대조를 먼저 세우는 것으로 대응했습니다.

남은 것도 분명합니다.

- **서명만으로 막지 못하는 것이 있습니다.** 가로챈 내부 토큰의 재전송(`aud`·`jti` 없음)과 게이트웨이 Pod 탈취 시 개인키 반출입니다. 이에 대한 당시 분석·결정 기록은 없고, Cloud KMS로 옮길지도 판단하지 않았습니다.
- **실트래픽 아래의 전환은 확인하지 않았습니다.** 롤아웃은 빈 클러스터 위의 리허설입니다.
- **사용자 토큰 회전을 GKE 운영 구성으로 완주한 기록은 없습니다.** 드릴은 minikube에서 Secret Manager·CSI·Workload Identity 없이 한 축만 실증했습니다. 드릴 overlay는 개인키 배타 소유 규칙을 의도적으로 어기므로 운영 매니페스트로 올리지 않으며, 운영 base의 user-service는 replica 1개입니다(드릴은 3~4개).
- **자연스러운 롤아웃에서 401 창이 얼마나 자주 열리는지는 모릅니다.** 6번 시도에서 모두 나오지 않았고, "열리면 이렇게 된다"까지만 보였습니다.
- **관측과 부하 측정에도 빈칸이 있습니다.** 게이트웨이 event-loop 지연은 직접 계측하지 않고 관리 포트 probe로 대신했고, 부하 측정에는 같은 노드에 띄운 k6의 경합이 섞여 있으며, 인증 실패 알림 임계는 아직 정하지 않았습니다.
- **담이 허용한 다른 길은 따져 보지 않았습니다.** Prometheus Pod 경로를 위조 경로로 분석하거나 측정한 기록이 없고, 허용 라벨(`app: gateway`)을 흉내 내는 Pod는 매니페스트 단계의 lint만 막습니다. 실행 중인 클러스터에서 그 라벨로 Pod를 띄우는 것을 막는 장치는 없습니다.
