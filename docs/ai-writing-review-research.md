# 한국어 개발 블로그의 AI식 문장 검토: 조사와 적용 기준

조사일: 2026-10-01. 적용 대상: 이 저장소의 한국어 Markdown/MDX 개발 글. 글의 **품질을 편집**하기 위한 자료이며 작성 주체를 판정하는 도구가 아니다. 실행 절차는 독립 스킬 [korean-blog-review](../.agents/skills/korean-blog-review/SKILL.md)에 있다.

## 1. 먼저 구분할 세 가지 문제

1. **언어적 규칙성**: 지나친 연결어·쉼표·em dash, 같은 모양의 문단, 반복적인 목차와 결론, 장식용 아이콘. 독자에게 기계적인 느낌을 줄 수 있지만 개별 글의 AI 작성 여부를 증명하지 않는다. 종결어미의 종류나 혼용 자체는 결함으로 보지 않는다.
2. **내용의 비어 있음**: 구체적 조건·관찰·원인·근거 대신 `중요하다`, `효율적이다`, `다양하다` 같은 평가가 이어지는 것. 블로그에서 더 큰 품질 문제다. 사람도 이런 글을 쓸 수 있다.
3. **사실 오류와 저자성 오류**: 없는 수치·로그·인용·경험을 만들거나, 예상 효과를 실제 측정 결과로 쓰거나, 남의 설명을 출처 없이 재서술하는 것. 문장만 매끄럽게 고쳐서는 해결되지 않는다.

따라서 검토 순서는 **근거 → 저자의 판단 → 구성 → 문장 → 수정 후 사실 대조**다. AI 탐지기 점수나 금지어 개수로 게시 여부를 정하지 않는다.

## 3. 독자가 흔히 ‘AI 티’로 느끼는 문장: 관찰 목록

아래는 위의 한국어 연구, 국립국어원의 명료성 지침, 공개 편집 스킬들을 토대로 만든 **검토용 질문**이다. 항목의 표현 자체가 AI 글임을 뜻하지는 않는다. 각 문장이 독자에게 어떤 정보와 판단을 주는지 보고 고친다.

| 신호 | 이 블로그에서 보일 수 있는 형태 | 편집 판단 |
| --- | --- | --- |
| 추상적 칭찬·중요성 선언 | `안정적인 아키텍처를 구축했습니다`, `매우 중요한 역할을 합니다` | 안정성의 기준, 적용 범위, 관찰 결과를 제시할 수 있는가? 없으면 단정 강도를 낮춘다. |
| 범용 도입 | `오늘날 빠르게 변화하는 개발 환경에서…`, `이번 글에서는 … 살펴보겠습니다` | 글의 실제 장애·질문·측정 조건으로 곧장 시작할 수 있는가? |
| 출처 없는 구체성 | `성능이 3배 개선됐습니다`, `운영 비용을 크게 절감했습니다` | 원자료의 기간, 비교 조건, 분모, 명령, 로그 또는 링크가 있는가? 없으면 발표하지 않는다. |
| 경험의 의인화·가짜 회고 | `저희 팀은 밤새 원인을 추적했습니다` | 사용자가 제공한 실제 기록인가? 아니라면 경험을 만들어 내지 않는다. |
| 반복되는 평가적 마무리 | 매 절 끝의 `이 점이 핵심입니다`, 마지막의 보편적 교훈 | 앞 절에 없는 결과·한계·다음 조건을 더하는가? 아니면 삭제한다. |
| 포장된 대비 | `단순한 캐시가 아니라 사용자 경험의 혁신입니다` | 비교 대상이 실제 대안이나 흔한 오해인가? 아니면 확인된 효과만 적는다. |
| 균일한 구조와 과한 정리 | 매 절이 `배경→장점 세 가지→요약`, 모든 줄이 굵게 표시 | 그 구조가 글의 인과관계·읽기 순서에 필요한가? 내용별로 형식을 달리한다. |
| 접속어·지시어의 기계적 반복 | `이러한`, `해당`, `또한`, `따라서`, `이를 통해`가 연속 | 앞 문장 없이도 대상이 분명한가? 구성요소 이름과 동사로 바꾸거나 연결어를 지운다. |
| 번역투·명사화·수동형 | `확인이 이루어졌습니다`, `성능 향상을 위한 최적화의 수행` | 주체와 동작을 `측정했습니다`, `줄였습니다`처럼 쓸 수 있는가? |
| 필요 없는 쉼표 | `따라서,`, `그리고,`의 습관적 사용 | 쉼표가 문장 해석이나 호흡에 실제로 도움이 되는가? |
| em dash와 아이콘의 장식적 반복 | 절마다 `—`로 극적인 전환을 만들거나 모든 제목에 `💡`, `🚀`을 붙임 | 구두점과 아이콘이 의미·상태·동작을 나타내는가? 그러지 않으면 평범한 문장과 제목으로 고친다. 실제 UI·도표의 기능성 아이콘은 별개다. |
| 영어 동사의 무리한 대응 | `로그를 박는다`, `문제를 닫는다`, `조용히 사라진다`, `판정했다` | 누가 무엇을 했는지 먼저 확인한다. 기록·저장·종료·커밋·누락·검증·결론 중 실제 사건에 맞는 동사를 고른다. 단어 자체를 금지하지 않는다. |
| 과도한 완곡 또는 과도한 확신 | `~할 수 있을 것으로 보입니다`의 연속 / `완벽하게 해결했습니다` | 관찰·추정·계획을 구분하고, 확인한 조건 안에서만 단언한다. |
| 독자 수준과 맞지 않는 설명 | 독자에게 익숙한 정의를 여러 번 설명하거나 낯선 핵심 개념을 건너뜀 | 대상 독자가 결론을 따라가는 데 필요한 설명만 남긴다. |

예를 들어 `이러한 접근은 시스템 안정성과 성능을 동시에 획기적으로 개선합니다`는 수치와 조건이 없는 평가다. 자료에 `중복 주문 0건`, `p95 420ms→310ms`, 같은 환경의 비교가 **실제로 있다면** 각각의 관찰과 조건을 적는다. 그런 자료가 없다면 `이 방식은 중복 처리를 막도록 설계했습니다. 성능 효과는 아직 측정하지 않았습니다`처럼 관찰 가능한 수준으로 쓴다. 이 예시 수치는 설명용 가정이며 원고에 옮겨 적을 사실이 아니다.

## 4. 탐지기와 ‘사람처럼 보이기’ 기법의 한계

- [OpenAI가 공개했던 영문 탐지기 설명](https://openai.com/index/new-ai-classifier-for-indicating-ai-written-text/)은 영문 평가에서 AI 글의 26%만 `AI 가능성이 높음`으로 잡고 인간 글의 9%를 잘못 표시했다고 기록한다. 그 도구는 정확도가 낮아 중단됐고, OpenAI는 비영어권·코드에서 성능이 더 낮다고 명시했다. 이는 **그 특정 도구의 과거 평가**이지 모든 현재 탐지기의 수치가 아니다.
- 한국어 KatFishNet 연구 자체도 장르 제한과 인간·AI 혼합 편집 글 미포함을 한계로 든다. 기술 블로그 한 편에 `AI 확률`을 붙여 품질 평가로 삼을 근거가 없다.
- 의도적 오탈자, 어색한 동의어 치환, 무작위 문장 길이 변화, 쉼표 일괄 삭제는 사실성·가독성을 해칠 수 있다. “탐지기 회피”보다 저자 기록과 독자 질문에 맞는 편집이 목적이다.
- em dash의 사용 빈도는 모델·장르·프롬프트에 따라 다르다. [여러 모델을 같은 프롬프트에서 비교한 2026년 실험](https://www.ruixiangtang.net/emdash.html)은 모델 간 차이가 커서 `모든 모델이 em dash를 남용한다`는 일반화가 성립하지 않음을 보여 준다. 반복적인 수사 장치인지 살피되, 한 번 등장했다고 고치지 않는다.
- [Google 검색 안내](https://developers.google.com/search/blog/2023/02/google-search-and-ai-content?hl=ko)는 적절한 AI 활용 자체를 금지하지 않는다. [사용자 중심 콘텐츠 자가 평가](https://developers.google.com/search/docs/fundamentals/creating-helpful-content?hl=ko)는 독창적인 정보·분석, 직접 경험, 출처, 명확한 제목과 유용성을 묻는다. 이 기준은 탐지 점수보다 이 블로그의 게시 검토에 가깝다.
- AI가 초안을 크게 작성한 사실이 독자에게 글의 생산 과정을 판단하는 데 중요하다면 [Google의 `Who, How, Why` 안내](https://developers.google.com/search/docs/fundamentals/creating-helpful-content?hl=ko)에 따라 제작 방식 설명을 고려한다. 이 문서는 일률적인 공개 문구를 강제하지 않는다.

## 5. 공개 스킬 비교: 가져올 방법과 버릴 방법

공개 GitHub 스킬은 **도구의 주장과 설계**를 보여 주며, 효과가 독립적으로 검증됐다는 증거는 아니다. 이 저장소에 설치하지 않고 필요한 편집 원칙만 비교했다.

## 6. 이 저장소에 적용한 결정

- 기존 `developer-blog-writer` 스킬의 글 유형별 점검을 유지하되, 종결어미 고정 규칙은 제거했다. 과거 사용자 지시에 따라 **저장소의 기존 글 본문은 어조·구성 견본으로 쓰지 않는다**.
- 검토 절차는 독립 `korean-blog-review` 스킬로 제공한다. `developer-blog-writer`가 새 글이나 큰 수정물을 전달하기 전에도 적용한다. 핵심 주장의 근거가 없으면 게시 준비 완료로 보고하지 않는다.
- 검토 결과는 `확인한 근거 / 고친 주요 부분 / 저자 확인 사항 / 남은 한계`로 짧게 전달한다. 발견한 표현을 모두 바꿀 의무는 없으며, 지적에는 실제 문장과 이유를 붙인다.
- 자동 탐지기·금지어 점수·쉼표 비율은 게시 게이트로 채택하지 않는다. 맞춤법과 빌드는 각각 문장 오류와 렌더링 오류를 확인할 뿐 사실과 목소리를 보증하지 않는다.

### 조사 범위와 남은 검증

한국어 실증 자료는 학습자 글·논설문·초록에 집중되어 있으며, 한국어 개발 블로그를 대상으로 한 검증은 이번 조사에서 확인하지 못했다. 따라서 이 절차의 효과는 이후 실제 초안에서 **근거 누락 감소, 수정 후 사실 보존, 독자의 이해도**로 평가하는 편이 타당하다. 특정 어휘 출현 빈도나 탐지기 점수로 성공을 선언하지 않는다.
