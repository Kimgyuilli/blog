# 한국어 개발 블로그 원고 검토: 다섯 단계

새 글이나 큰 수정의 전달 전에 적용한다. 본문을 검토하며 코드 블록, 출처의 직접 인용, URL, 화면 자산의 표기를 문체 검사 대상으로 삼지 않는다. 낱말이나 문장 부호가 발견됐다는 이유만으로 수정하거나 AI 작성이라고 판단하지 않는다. 검토 요청에는 위치·이유·수정 방향을 보고하고, 수정 요청에는 고친 뒤 원자료와 대조한다.

## 1. 근거와 단정 강도

핵심 주장을 사용자 기록, 확인한 코드·로그, 외부 원문, 저자의 해석, 미확인 가설로 구분한다. 숫자, 날짜, 버전, API 동작, 성능 효과, 장애 원인, 인용, 작업 완료 여부를 우선 대조한다. 관찰한 결과와 기대 효과를 섞지 않는다. 결론에 필요한 사실이 빠졌다면 구체적으로 질문한다. 그 밖에는 확인된 범위로 좁히거나 근거 없는 문장을 덜어 낸다. 경험, 측정값, 로그, 출처를 그럴듯하게 만들어 넣지 않는다.

## 2. 저자의 판단과 독자의 질문

이 글이 답할 독자의 질문을 한 문장으로 적는다. 주요 절이 관찰, 조건, 선택 기준, 대안, 반례, 검증 결과, 한계 중 무엇을 보태는지 확인한다. 개념 글은 직접 경험 없이도 정확한 출처와 예시로 성립할 수 있다. 장애 글은 증상·원인 추론·수정·재검증을 연결하는 증거가 필요하다. 결정 글에는 실제 기준이, 실험 글에는 조건과 분모가 필요하다. 독자가 결론을 평가하는 데 필요한 세부 사항을 보존한다.

## 3. 구성과 눈에 띄는 반복

도입, 절의 순서, 목록, 강조, 끝맺음을 살핀다. 정보가 늘지 않는 요약과 의례적인 연결 문장을 줄인다. 코드의 순서나 비교를 이해시키는 제목·표·목록은 남긴다.

- **Em dash(`—`)**: 여러 문단이 같은 위치에서 극적인 전환이나 대비를 만들면 관계를 직접 서술할 수 있는지 본다. 마침표·쉼표·괄호·쌍점이나 새 문장이 더 명확하면 바꾼다. 인용이나 의도적인 끊김은 유지한다. 허용 횟수를 정하지 않는다.
- **아이콘·이모지**: 제목, 목록, 강조 상자마다 붙은 표시가 실제 상태·동작·개념을 구분하는지 확인한다. 장식만 반복되면 덜어 낸다. 이 본문 검토로 UI 컴포넌트나 이미지를 수정하지 않는다.
- **굵게 표시·구분선·세 항목 나열**: 실제 정보의 층위를 드러내는가? 유용한 3단계 절차나 비교 표를 패턴과 닮았다는 이유로 평탄하게 만들지 않는다.
- **상투적인 수사**: 근거 없는 `중요합니다`, `핵심입니다`, `단순히 A가 아니라 B`, 거창한 결론, 절마다 붙는 한 줄 교훈을 살핀다. 자료가 허용하는 관찰이나 결과로 바꾼다.

## 4. 한국어 문장과 번역체 오염

`누가, 무엇을, 어떤 조건에서, 어떻게 했는가`를 확인한다. 영어 동사의 넓은 뜻, 수동 구조, 은유를 한국어에 곧바로 대응시키면 문법이 맞아도 실제 기술 사건이 흐려질 수 있다. 다음 말은 금지어가 아니라 **목적어와 사건을 확인할 후보**다.

| 표현 후보 | 확인할 내용과 가능한 수정 |
| --- | --- |
| `박는다` | `로그를 박는다`는 `로그를 남긴다`, `캐시에 값을 박는다`는 `값을 저장한다`가 정확할 수 있다. 저자가 의도한 구어 표현이고 실제 동작을 잘 나타내면 유지한다. |
| `닫는다` | 이슈·연결·트랜잭션·요청 중 무엇을 말하는지 확인한다. 실제 사건은 종료, 해제, 커밋, 롤백, 응답, UI 닫기 중 하나일 수 있다. `연결을 닫는다`가 정확한 맥락도 있다. |
| `조용히 사라진다` | 메시지가 버려졌는지, 기록이 삭제됐는지, 요청이 시간 초과됐는지, 예외가 무시됐는지, 로그가 남지 않았는지 확인한다. 원자료가 보여 주는 사건만 쓴다. |
| `판정했다` | 테스트, 검증 규칙, 분류기, 사람이 각각 무엇을 출력하거나 결론 냈는지 밝힌다. 실제 판정 행위라면 단어를 유지한다. |

`이러한`, `해당`, `이를 통해`, `또한`, `따라서`, `특히`가 지시 대상과 논리 관계 없이 반복되는지 살핀다. `확인이 이루어졌다` 같은 명사화·수동 표현은 실제 행위자를 드러낼 수 있는지 본다. 추상적인 평가 형용사에는 평가 기준이 있는지 확인한다. 기술 용어와 필요한 정의는 유지한다. 쉼표는 뜻과 호흡을 기준으로 점검한다. 접속어·절 뒤의 불필요한 쉼표를 덜되, 열거·수치·코드·뜻 구분에 필요한 쉼표를 보존한다.

**종결어미는 제한하지 않는다.** `-습니다`, `-다`, `-해요`, 질문형, 대화적인 종결을 의도에 따라 사용할 수 있다. 혼용 자체를 오류로 표시하지 않는다. 독자를 헷갈리게 하거나 화자가 바뀐 것처럼 보이는 전환만 검토한다.

## 5. 수정 후 대조와 전달

뜻과 흐름이 좋아지는 곳만 고치고 잘 작동하는 문장은 둔다. 원자료와 대조해 주장, 수치, 조건, 인용, 코드, 명령, 링크, 출처, 불확실성이 빠지거나 생기지 않았는지 확인한다. 핵심 근거가 없으면 게시 준비가 끝났다고 하지 않고 저자에게 필요한 질문을 남긴다. 사람처럼 보이기 위한 오탈자, 무작위 문장 길이 변화, 억지 동의어, 쉼표 일괄 삭제를 하지 않는다.

검토만 했다면 **위치·문제·이유·수정안**을 제시하고 사실 확인이 필요한 항목을 문체 제안과 구분한다. 수정했다면 **주요 변경·확인한 근거·저자 확인 사항·남은 한계**를 짧게 보고한다. AI 작성 확률은 보고하지 않는다. 패턴이 보이지 않는다는 사실만으로 정확성이나 독창성을 보증하지 않는다.
